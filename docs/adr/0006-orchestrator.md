# ADR 0006. 메인 오케스트레이터 + 작업 세션 + 엔진 프로필 폴백


> 2026-10-16 후속 결정: 신규 auto 작업자의 배정은 `runs/worker_routing.py`의 task_type 정책으로 대체했다. Antigravity 포함, 모델별 quota·fallback·대화 보존·배정 영수증·idle reroute는 [API 계약](../api-contract.md#작업자-task-routing-2026-10-16)을 따른다. 아래의 과거 native-only auto/Luna 기본·디자인 native Claude 고정 설명은 레거시 세션의 이력이며 신규 auto 작업자에 적용하지 않는다. 메인·접수·별도 회의/날씨 경로는 기존 계약을 유지한다.
- 상태: 채택 (2026-10-11)
- 결정자: 사용자("하나의 메인이 오케스트레이션하는 형태", "클로드코드 고정, 토큰 사용량 때문에 못 쓰면 여차하면 codex 까지", "상세페이지에서 직접 지시도 허용", "기존 세션 목록은 유지")

## 결정

### 세션 종류
| kind | 무엇 | 목록 |
|---|---|---|
| `chat` | 기존 단일 에이전트 대화(이전 데이터 포함) | 사이드바 |
| `orchestrator` | 사용자가 대화하는 메인. 일을 작업 세션에 맡기고 결과를 보고한다 | 사이드바 |
| `worker` | 오케스트레이터가 만든 작업 세션. `parent_id` = 오케스트레이터 | 오케스트레이터 화면 오른쪽 탭 |

사용자는 작업 세션에도 직접 지시할 수 있다(상세 페이지). 그 결과도 오케스트레이터에게 보고된다.

### 오케스트레이터 도구(MCP)
오케스트레이터 Run 에만 stdio MCP 서버 `ttakkari`(`python -m ttakkari.orchestrator.mcp_server`)를 붙인다.
도구: `spawn_worker` `message_worker` `list_workers` `get_worker` `stop_worker` `account_usage`(계정별 상태, 아래 "놀고 있는 계정 먼저").
MCP 서버는 백엔드 HTTP(`/api/orchestrator/*`)를 부른다. Run 은 백엔드 프로세스 안의 매니저가 돌려야 해서 DB 를 직접 만지지 않는다.
인증은 오케스트레이터 세션 하나에 묶인 짧은 JWT(`aud=ttakkari-orch`, `sid`)다. 그 세션의 작업 세션만 보고 만질 수 있다.

### 결과 보고 루프
작업 세션 Run 이 끝나면 오케스트레이터 세션에 `origin=report` Run 을 넣는다(결과 3000자·오류 요약).
아직 시작 안 한 보고 Run 이 있으면 거기에 덧붙여 보고 여러 개를 한 턴에 처리한다.
오케스트레이터의 한 턴은 짧다(맡기고 끝낸다). 사용자 메시지는 기존 세션 대기열에 쌓이므로 응답을 기다리지 않고 계속 보낼 수 있다.

### 엔진 프로필과 폴백
계정은 DB `engine_accounts`(이름·엔진·계정 폴더·켜기·우선순위)에 있고 설정 > 계정에서 고친다(`/api/accounts`). 테이블이 비어 있으면 아래 설정값으로 한 번 채운다.
기본 계정(계정 폴더 비움)은 엔진 기본 위치를 쓴다. 백엔드를 띄운 셸의 `CLAUDE_CONFIG_DIR`·`CODEX_HOME` 은 자식에게 넘기지 않는다(Orca 터미널에서 띄우면 Orca 의 Codex 계정이 새던 문제).
`TTAKKARI_ENGINE_PROFILES`(JSON 배열, 순서 = 우선순위). 기본 `[{"name":"claude","engine":"claude"},{"name":"codex","engine":"codex"}]`.
Claude 계정을 여러 개 쓰려면 `{"name":"claude-2","engine":"claude","config_dir":"~/.claude-2"}`(`CLAUDE_CONFIG_DIR`), Codex 는 `config_dir` 가 `CODEX_HOME`.
- 세션 엔진 `auto`(오케스트레이터 기본·작업 세션 기본): 모든 프로필을 순서대로.
- 세션 엔진 `claude`/`codex`: 그 엔진의 프로필만(계정 전환만, 엔진은 안 바꾼다).
Run 이 사용량 한도로 실패하면(출력·오류 문구 휴리스틱, 아래 한계) 그 프로필을 `profile_cooldown_seconds`(기본 30분) 쉬게 하고 같은 Run 안에서 다음 프로필로 다시 실행한다. 이벤트 `engine.fallback`.
### 한도 전환·대기(2026-10-13)
- 감지: 오류·stderr·결과 문구(`USAGE_LIMIT_RE`: session/weekly/usage limit, limit reached, quota 등)에 더해 Claude 구조화 이벤트(`rate_limit_event.status=rejected`, assistant `error=rate_limit`)도 한도로 본다. 초기화 시각은 `resets 3pm (Asia/Seoul)`·`resets Oct 20, 3pm`·`resets Mon 3pm`·`limit reached|<epoch>`·Codex `try again at ...` 에서 읽는다. 구조화 이벤트 형태는 가짜 엔진으로만 검증했고 실제 CLI 출력으로는 확인하지 못했다.
- 계정은 초기화 시각까지 쉰다(`profiles._cooldown`, app_settings `account_limits` 에도 적어 재시작해도 유지). 사용량 화면(캐시)이 5시간·주간 100% 로 보이는 계정도 초기화 전에는 부르지 않는다(모델별 주간 한도는 무시).
- 전환: 우선순위상 다음 계정으로 같은 Run 안에서 이어 간다. 이미 대화가 있는 계정이면 엔진 세션을 resume(그 계정이 쉬는 동안 다른 계정에서 오간 대화만 덧붙임), 처음이거나 엔진이 다르면 대화·이 Run 의 진행(최근 도구 호출·결과)·기억 검색 결과를 요약해 프롬프트에 싣는다(`engine.fallback.mode`). 엔진 간 세션 공유는 불가능해서 요약 전달만 현실적이다.
- 오케스트레이터가 다른 엔진으로 넘어가면 `orchestrator_fallback_models`(기본 claude=opus/medium, codex=gpt-6.1-sol/high)로 모델·생각 수준을 맞춘다. 직접 그 엔진 모델을 고른 Run 과 일반 대화는 건드리지 않는다.
- 모든 계정이 한도면 실패로 끝내지 않는다. Run 을 `queued` 로 두고 `run.waiting` 을 남기며 푸시로 알린다. 가장 이른 초기화 시각에 같은 Run 을 다시 돌리고(인계문은 `run.waiting.handoff`), 계정 한도 해제·계정 켜기는 즉시 재시도한다. 같은 세션의 다음 지시는 이 Run 뒤에 선다. 한 Run 의 대기가 `max_limit_waits`(기본 8)를 넘으면 실패로 끝낸다.
- 작업 세션(worker)도 같은 경로라 같은 동작이다. 대기 중에는 오케스트레이터에게 보고가 가지 않는다(Run 이 끝나지 않았으므로).

### 놀고 있는 계정 먼저(2026-10-13)
- 순서 규칙(`profiles.choose`, 2026-10-15): ① 신선한 사용량이 있는 계정 ② `상한 여유 / (다른 실행 중 Run 수 + 1)`가 큰 계정(동률이면 더 가까운 초기화 시각) ③ 모델 이름이 가리키는 엔진 선호 ④ 다른 Run 이 쓰지 않는 계정 ⑤ 기존 우선순위. 이 점수는 측정 주기 사이의 동시 배정을 분산하는 기준이며 실제 소모량 예측이 아니다. stale/null·측정 후 초기화된 값은 순위에 쓰지 않으며, 해당 후보끼리는 모델·유휴·우선순위로 비교한다. 알 수 없는 후보 하나 때문에 신선한 후보 전체의 비교를 끄지 않는다. `max_used_percent` 상한에 닿은 마지막 측정값은 낡아도 차단 근거로 유지한다. 해당 창 초기화·새로운 상한 미만 측정·상한 상향 때 해제되며 초기화 시각이 없으면 90초 후 다시 판단한다.
- 적용 지점: 기획·작업 세션·일반 대화의 Run 시작과 한도 전환. 고정 엔진 세션도 그 엔진 안에서 사용량을 비교한다. 전환할 때는 그 사이 다른 Run 이 한도에 걸린 계정도 다시 걸러 낸다. 접수는 `desk_engine_order`의 엔진 순서를 지키며 같은 엔진의 후보끼리 비교한다. 기획도 Run 당 여유에 다른 실행 수를 반영하며, 미측정 후보끼리는 시작 시 유휴 우선 규칙을 쓰지 않는다. 계정이 바뀌면 저장된 해당 계정의 엔진 대화를 이어 쓰고, 그동안 다른 계정에서 오간 대화는 `_handoff_context`로 전달한다(허용 모델 `orchestrator_fallback_models` 적용은 그대로).
- 2026-10-14 수정: 기존의 auto 작업자 전용 분산과 기획 시작 시 우선순위 고정은 접수·기획의 Daddy 계정 쏠림을 막지 못해 위의 전 역할 사용량 비교로 대체했다.
- "쓰는 중"은 매니저가 메모리(`profiles._in_use`, run id → 계정 id)에 적는다. 같은 프로세스에서 고르는 일과 적는 일 사이에 await 가 없어 다음 배정은 앞선 배정 수를 즉시 반영한다. 자기 Run 은 다른 실행 수에서 제외하고 종료·취소·한도 대기 시 해제한다. 잔여가 비슷한 계정은 분산되지만 여유가 압도적으로 큰 계정은 바빠도 선택될 수 있다. 재시작하면 Run 도 함께 끝나서 DB 에 두지 않는다.
- 엔진을 고정한 세션(`claude`/`codex`)은 그 엔진 계정만, 회사 업무 세션은 회사에 들어온 계정만, 회사 모드 순서·켜기로 후보다(범위 규칙 그대로). 일반 개발·조사·검증은 `spawn_worker(engine="auto")`로 매 턴 두 엔진의 사용량을 비교한다. 모델 이름은 동일 등급 상대 모델(`model_counterparts`) 선택을 위한 선호이고 엔진 잠금이 아니다. 디자인·시각 작업은 `engine="claude"`로 고정하고 부족하면 PMS WBS에 기록한다. 배정마다 `account_usage`를 확인한다. 일반 작업의 기존 고정 엔진 작업자가 한도를 기다리면 진행 기록 확인 → 중단 → 미완료 부분을 auto 작업자로 재배정하며 이미 실행한 부작용은 반복하지 않는다.
- 한계: 계정을 옮기면 그 계정에 이미 있던 엔진 대화를 못 이어 쓸 수 있다(인계문으로 대신한다). "쓰는 중" 판단은 이 서버가 시작한 Run 만 센다(엔진 CLI 를 사용자가 직접 돌리는 것은 모른다). 잔여 한도는 다른 클라이언트의 사용과 측정 주기 사이에 변할 수 있다.

### `account_usage` 도구(오케스트레이터 전용)
- `GET /api/orchestrator/accounts/usage` 를 부른다. 계정마다 엔진·범위(personal/work)·켜짐·우선순위·`available`·한도 대기(`limit.waiting/until/reason`)·`running_runs`·`headroom_per_run_percent`(신선한 상한 여유를 현재 실행 수 + 1로 나눈 신규 배정 점수, 미확인 시 null)·지정 가능한 모델(설정 `engine_models`)·오케스트레이터 허용 모델·사용량(5시간·주간·모델별 주간의 사용/잔여 퍼센트, 초기화 시각, 측정 시각, 나이, `stale`)을 낸다.
- 사용량은 앱이 마지막으로 본 값만 쓴다. 채우는 쪽은 둘이다(2026-10-13).
  - 주기 수집기(`runs/usage_collector.py`): 켜진 계정마다 사용량 조회 API(Claude OAuth `/api/oauth/usage`, Codex `wham/usage`)를 읽는다. 모델 호출은 없다. 평소 5분(`usage_poll_seconds`), Run 이 그 계정을 쓰는 중이거나 5시간·주간 잔여가 20% 미만이면 90초(`usage_poll_busy_seconds`, `usage_low_remaining_percent`). 알려진 초기화 시각이 지나면 바로 한 번 더 읽는다. 실패하면 두 배씩 늦추고(최대 30분) 주기에 ±15% 지터, 계정 사이에 0.5~2초 간격을 둔다. 실측: 계정 7개(Claude 4·Codex 3) 모두 `source=api` 로 5시간·주간·(Claude)모델별 주간 퍼센트와 초기화 시각을 받았다.
  - 실행 스트림의 `rate_limit_event`: Run 이 도는 동안 이벤트가 올 때마다 반영한다(Claude만. Codex 는 API 수집이 90초 주기로 대신한다).
  - 저장: `account_usage_samples`(0015). 계정별 가장 최근 행이 최신값이고 재시작하면 거기서 캐시를 복원한다. 나머지는 이력(14일, `usage_history_days`)이며 계정별 마지막 행은 지우지 않는다. 같은 값은 10분, 바뀐 값도 1분에 한 번만 쓴다. 토큰은 어디에도 두지 않는다.
  - 소모 속도: 이력에서 같은 초기화 주기 안의 최근 구간(5시간 창 2시간, 그 밖 24시간)의 증가분으로 `burn_percent_per_hour`, 이 속도로 찰 때까지 `exhausts_in_seconds`, 초기화 전에 차는지 `exhausts_before_reset` 을 계산한다. 구간이 5분 미만이거나 줄었으면 null.
- (이전 설명) 사용량 화면이 채우는 캐시와 실행 스트림의 `rate_limit_event` 만 쓰던 때에는 수집기가 없어 화면을 열지 않으면 비어 있었다. 이 도구는 새로 조회하지 않으므로 인증 파일·키체인을 읽지 않고, 계정 폴더·이메일·토큰도 내지 않는다. 값이 없으면 `usage: null`, `usage_stale_seconds`(기본 15분, 수집 주기의 3배)보다 오래됐으면 `stale: true`, 측정 뒤 초기화 시각이 지났으면 `reset_since_measured: true`(잔여 null).
- 회사 업무 오케스트레이터(`sessions.pool=work`)는 회사에 들어온 계정만 회사 모드 순서·켜기로 본다. 개인 오케스트레이터는 전체를 보고 `scope` 로 구분한다.

엔진 대화 ID 는 계정 id 별로 `sessions.engine_sessions` 에 둔다(이름을 바꿔도 이어진다). 처음 쓰는 프로필로 넘어가면 최근 대화 8턴을 프롬프트 앞에 붙여 맥락을 넘긴다.

## 버린 것
- Agent SDK·app-server 상주 오케스트레이터: 지시 1회 = 프로세스 1회 구조(ADR 0002)를 유지하는 편이 재시작 복구·취소가 단순하다.
- 오케스트레이터가 서브에이전트(엔진 내장 Task)로 일하기: 진행·결과물이 UI 에 탭으로 안 보이고, 사용자가 직접 지시할 수 없다.
- MCP 서버가 DB 직접 접근: 매니저(동시 실행 슬롯·대기열 잠금)를 우회한다.

## 2026-10-16 한도 대기 재평가·재개 보존

- 고정 작업·일반 대화의 기본값은 한도 시 같은 계열 → 작업에 맞는 다른 엔진/풀로 인계다. `strict_engine=true`는 해당 엔진의 reset 대기를 유지한다. 계정 전체 여유가 아니라 요청 모델의 5시간·주간 pool 창을 각각 판단한다.
- queued quota wait는 active coordinator가 재평가하며, 적합한 후보가 생기면 과거 reset 시각을 기다리지 않고 같은 Run으로 재개한다. lease가 있는 Run·취소·재시작 backoff는 제외한다. 시작 시각·checkpoint·진행 인계와 모델별 대화 키를 보존한다.
- 마지막 실행 모델과 요청 모델은 다를 수 있으므로 `run.usage.routing_request`로 원래 요청을 보존한다. legacy account-only 대화 ID는 원래 모델에서만 재사용한다.
- 권한 거부 줄에 포함된 quota/429 문자열은 한도 증거가 아니다. 샌드박스 권한 거부를 공급자 변경으로 재시도하지 않는다.
- 아래 초기 기록의 메모리 전용 cooldown·고정 엔진 대기·account-only 대화 키 설명은 이 보완 및 위의 영속화 계약으로 대체됐다.

## 알려진 한계
- 사용량 한도 판별은 문구 휴리스틱이다(`usage limit`, `hit your limit`, `rate limit`, `quota`, `429` 등). 엔진 문구가 바뀌면 폴백이 안 걸리고 그냥 실패한다(확인 필요: 실제 한도 도달 시 문구).
- 쿨다운은 메모리에만 있다. 서버를 재시작하면 처음부터 다시 시도한다.
- 프로필을 바꿀 때 최근 지시·답과 같은 Run에서 관측된 일부 도구 호출·결과를 넘긴다. 엔진 내부의 모든 도구 상태를 완전히 옮기지는 못한다.

## 2026-10-12 보완: 세션 한도와 맥락 인계

- Claude의 실제 `You've hit your session limit · resets 7:20pm (Asia/Seoul)` 문구를 사용량 한도로 분류한다. 초기화 시각은 표시된 시간대의 다음 해당 시각으로 해석한다.
- 한도에 걸린 계정은 초기화 전까지 후보에서 제외한다. 모든 활성 계정이 쉬는 중이면 엔진을 다시 호출하지 않고 Run에 한도 대기 오류를 남긴다. 한 Run에서는 우선순위 순서대로 각 계정을 최대 한 번 호출한다.
- 다음 계정의 엔진 대화 ID가 없으면 최근 대화 8턴을 전달한다. 같은 Run에서 앞선 계정이 실패했을 때는 엔진 종류와 관계없이 그 시도의 오류, 관측 가능한 메시지·도구 결과, 기억과 색인된 work-history 검색 결과를 제한된 길이로 전달한다. 이미 만든 작업 세션과 파일을 확인한 뒤 계속하도록 지시한다.
- 계정 순서는 전역 한 줄이다. 순서 변경 요청의 ID가 현재 목록의 일부여도 받아들이고, 빠진 계정은 기존 상대 순서대로 뒤에 둔다. 이는 목록 조회 이후 계정이 추가된 경우를 수용한다. 중복·존재하지 않는 ID는 400으로 거부하며 로그에는 ID 대신 개수만 기록한다.
