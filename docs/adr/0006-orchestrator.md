# ADR 0006. 메인 오케스트레이터 + 작업 세션 + 엔진 프로필 폴백

- 상태: 채택 (2026-10-11)
- 결정자: 사용자("하나의 메인이 오케스트레이션하는 형태", "클로드코드 고정, 토큰 사용량 때문에 못 쓰면 여차하면 codex 까지", "상세페이지에서 직접 지시도 허용", "기존 세션 목록은 유지")

## 결정

### 세션 종류
| kind | 무엇 | 목록 |
|---|---|---|
| `chat` | 기존 단일 에이전트 대화(이전 데이터 포함) | 사이드바 |
| `orchestrator` | 사용자가 대화하는 메인. 일을 작업 세션에 맡기고 결과를 보고한다 | 사이드바 |
| `worker` | 오케스트레이터가 만든 작업 세션. `parent_id` = 오케스트레이터 | 오케스트레이터 화면 오른쪽 탭 |

사용자는 작업 세션에도 직접 지시할 수 있다(상세 페이지). 그 결과도 오케스트레이터에게 보고된다.

### 오케스트레이터 도구(MCP)
오케스트레이터 Run 에만 stdio MCP 서버 `ttakkari`(`python -m ttakkari.orchestrator.mcp_server`)를 붙인다.
도구: `spawn_worker` `message_worker` `list_workers` `get_worker` `stop_worker` `account_usage`(계정별 상태, 아래 "놀고 있는 계정 먼저").
MCP 서버는 백엔드 HTTP(`/api/orchestrator/*`)를 부른다. Run 은 백엔드 프로세스 안의 매니저가 돌려야 해서 DB 를 직접 만지지 않는다.
인증은 오케스트레이터 세션 하나에 묶인 짧은 JWT(`aud=ttakkari-orch`, `sid`)다. 그 세션의 작업 세션만 보고 만질 수 있다.

### 결과 보고 루프
작업 세션 Run 이 끝나면 오케스트레이터 세션에 `origin=report` Run 을 넣는다(결과 3000자·오류 요약).
아직 시작 안 한 보고 Run 이 있으면 거기에 덧붙여 보고 여러 개를 한 턴에 처리한다.
오케스트레이터의 한 턴은 짧다(맡기고 끝낸다). 사용자 메시지는 기존 세션 대기열에 쌓이므로 응답을 기다리지 않고 계속 보낼 수 있다.

### 엔진 프로필과 폴백
계정은 DB `engine_accounts`(이름·엔진·계정 폴더·켜기·우선순위)에 있고 설정 > 계정에서 고친다(`/api/accounts`). 테이블이 비어 있으면 아래 설정값으로 한 번 채운다.
기본 계정(계정 폴더 비움)은 엔진 기본 위치를 쓴다. 백엔드를 띄운 셸의 `CLAUDE_CONFIG_DIR`·`CODEX_HOME` 은 자식에게 넘기지 않는다(Orca 터미널에서 띄우면 Orca 의 Codex 계정이 새던 문제).
`TTAKKARI_ENGINE_PROFILES`(JSON 배열, 순서 = 우선순위). 기본 `[{"name":"claude","engine":"claude"},{"name":"codex","engine":"codex"}]`.
Claude 계정을 여러 개 쓰려면 `{"name":"claude-2","engine":"claude","config_dir":"~/.claude-2"}`(`CLAUDE_CONFIG_DIR`), Codex 는 `config_dir` 가 `CODEX_HOME`.
- 세션 엔진 `auto`(오케스트레이터 기본·작업 세션 기본): 모든 프로필을 순서대로.
- 세션 엔진 `claude`/`codex`: 그 엔진의 프로필만(계정 전환만, 엔진은 안 바꾼다).
Run 이 사용량 한도로 실패하면(출력·오류 문구 휴리스틱, 아래 한계) 그 프로필을 `profile_cooldown_seconds`(기본 30분) 쉬게 하고 같은 Run 안에서 다음 프로필로 다시 실행한다. 이벤트 `engine.fallback`.
### 한도 전환·대기(2026-10-13)
- 감지: 오류·stderr·결과 문구(`USAGE_LIMIT_RE`: session/weekly/usage limit, limit reached, quota 등)에 더해 Claude 구조화 이벤트(`rate_limit_event.status=rejected`, assistant `error=rate_limit`)도 한도로 본다. 초기화 시각은 `resets 3pm (Asia/Seoul)`·`resets Oct 20, 3pm`·`resets Mon 3pm`·`limit reached|<epoch>`·Codex `try again at ...` 에서 읽는다. 구조화 이벤트 형태는 가짜 엔진으로만 검증했고 실제 CLI 출력으로는 확인하지 못했다.
- 계정은 초기화 시각까지 쉰다(`profiles._cooldown`, app_settings `account_limits` 에도 적어 재시작해도 유지). 사용량 화면(캐시)이 5시간·주간 100% 로 보이는 계정도 초기화 전에는 부르지 않는다(모델별 주간 한도는 무시).
- 전환: 우선순위상 다음 계정으로 같은 Run 안에서 이어 간다. 이미 대화가 있는 계정이면 엔진 세션을 resume(그 계정이 쉬는 동안 다른 계정에서 오간 대화만 덧붙임), 처음이거나 엔진이 다르면 대화·이 Run 의 진행(최근 도구 호출·결과)·기억 검색 결과를 요약해 프롬프트에 싣는다(`engine.fallback.mode`). 엔진 간 세션 공유는 불가능해서 요약 전달만 현실적이다.
- 오케스트레이터가 다른 엔진으로 넘어가면 `orchestrator_fallback_models`(기본 claude=opus/medium, codex=gpt-6.1-sol/high)로 모델·생각 수준을 맞춘다. 직접 그 엔진 모델을 고른 Run 과 일반 대화는 건드리지 않는다.
- 모든 계정이 한도면 실패로 끝내지 않는다. Run 을 `queued` 로 두고 `run.waiting` 을 남기며 푸시로 알린다. 가장 이른 초기화 시각에 같은 Run 을 다시 돌리고(인계문은 `run.waiting.handoff`), 계정 한도 해제·계정 켜기는 즉시 재시도한다. 같은 세션의 다음 지시는 이 Run 뒤에 선다. 한 Run 의 대기가 `max_limit_waits`(기본 8)를 넘으면 실패로 끝낸다.
- 작업 세션(worker)도 같은 경로라 같은 동작이다. 대기 중에는 오케스트레이터에게 보고가 가지 않는다(Run 이 끝나지 않았으므로).

### 놀고 있는 계정 먼저(2026-10-13)
- 순서 규칙(`profiles.choose`): ① 모델 이름이 가리키는 엔진 ② 한도 여유가 있고 지금 다른 Run 이 쓰지 않는 계정 ③ 기존 우선순위. 한도에 걸린 계정은 먼저 걸러지고(`limited_until`: 쉬는 시각 + 사용량 캐시 100%), 퍼센트 잔여로 순서를 바꾸지는 않는다(값이 낡거나 없을 수 있고 순서가 불안정해진다). 모두 바쁘면 우선순위 그대로다.
- 적용 지점: 한도 전환 때 다음 계정, 그리고 작업 세션·일반 대화의 Run 시작. 전환할 때는 그 사이 다른 Run 이 한도에 걸린 계정도 다시 걸러 낸다. 메인 오케스트레이터의 시작은 우선순위를 지킨다. 지시마다 계정을 옮기면 엔진 대화를 이어 쓰지 못하고 인계문을 매번 싣게 되며, 자기 작업 세션이 쓰는 계정이 바쁘다고 밀려나는 것도 이상하다. 오케스트레이터도 한도 전환 때는 같은 규칙이다(허용 모델 `orchestrator_fallback_models` 적용은 그대로).
- "쓰는 중"은 매니저가 메모리(`profiles._in_use`, run id → 계정 id)에 적는다. 같은 프로세스에서 고르는 일과 적는 일 사이에 await 가 없어, 작업 세션 여러 개를 연달아 띄워도 같은 계정에 몰리지 않는다. 한도 대기 중인 Run 은 계정을 쓰지 않는다. 재시작하면 Run 도 함께 끝나서 DB 에 두지 않는다.
- 엔진을 고정한 세션(`claude`/`codex`)은 그 엔진 계정만, 회사 업무 세션은 회사 그룹만 후보다(범위 규칙 그대로). `auto` 작업 세션은 엔진을 가리지 않고 놀고 있는 계정으로 가므로, 엔진이 중요하면 `spawn_worker` 에 engine·model 을 정한다.
- 한계: 계정을 옮기면 그 계정에 이미 있던 엔진 대화를 못 이어 쓸 수 있다(인계문으로 대신한다). "쓰는 중" 판단은 이 서버가 시작한 Run 만 센다(엔진 CLI 를 사용자가 직접 돌리는 것은 모른다).

### `account_usage` 도구(오케스트레이터 전용)
- `GET /api/orchestrator/accounts/usage` 를 부른다. 계정마다 엔진·범위(personal/work)·켜짐·우선순위·`available`·한도 대기(`limit.waiting/until/reason`)·`running_runs`·지정 가능한 모델(설정 `engine_models`)·오케스트레이터 허용 모델·사용량(5시간·주간·모델별 주간의 사용/잔여 퍼센트, 초기화 시각, 측정 시각, 나이, `stale`)을 낸다.
- 사용량은 앱이 마지막으로 본 값(사용량 화면이 채우는 캐시, 실행 스트림의 `rate_limit_event`)만 쓴다. 이 도구는 새로 조회하지 않으므로 인증 파일·키체인을 읽지 않고, 계정 폴더·이메일·토큰도 내지 않는다. 값이 없으면 `usage: null`, 15분보다 오래됐으면 `stale: true`, 측정 뒤 초기화 시각이 지났으면 `reset_since_measured: true`(잔여 null).
- 회사 업무 오케스트레이터(`sessions.pool=work`)는 회사 그룹 계정만 본다. 개인 오케스트레이터는 전체를 보고 `scope` 로 구분한다.

엔진 대화 ID 는 계정 id 별로 `sessions.engine_sessions` 에 둔다(이름을 바꿔도 이어진다). 처음 쓰는 프로필로 넘어가면 최근 대화 8턴을 프롬프트 앞에 붙여 맥락을 넘긴다.

## 버린 것
- Agent SDK·app-server 상주 오케스트레이터: 지시 1회 = 프로세스 1회 구조(ADR 0002)를 유지하는 편이 재시작 복구·취소가 단순하다.
- 오케스트레이터가 서브에이전트(엔진 내장 Task)로 일하기: 진행·결과물이 UI 에 탭으로 안 보이고, 사용자가 직접 지시할 수 없다.
- MCP 서버가 DB 직접 접근: 매니저(동시 실행 슬롯·대기열 잠금)를 우회한다.

## 알려진 한계
- 사용량 한도 판별은 문구 휴리스틱이다(`usage limit`, `hit your limit`, `rate limit`, `quota`, `429` 등). 엔진 문구가 바뀌면 폴백이 안 걸리고 그냥 실패한다(확인 필요: 실제 한도 도달 시 문구).
- 쿨다운은 메모리에만 있다. 서버를 재시작하면 처음부터 다시 시도한다.
- 프로필을 바꿀 때 최근 지시·답과 같은 Run에서 관측된 일부 도구 호출·결과를 넘긴다. 엔진 내부의 모든 도구 상태를 완전히 옮기지는 못한다.

## 2026-10-12 보완: 세션 한도와 맥락 인계

- Claude의 실제 `You've hit your session limit · resets 7:20pm (Asia/Seoul)` 문구를 사용량 한도로 분류한다. 초기화 시각은 표시된 시간대의 다음 해당 시각으로 해석한다.
- 한도에 걸린 계정은 초기화 전까지 후보에서 제외한다. 모든 활성 계정이 쉬는 중이면 엔진을 다시 호출하지 않고 Run에 한도 대기 오류를 남긴다. 한 Run에서는 우선순위 순서대로 각 계정을 최대 한 번 호출한다.
- 다음 계정의 엔진 대화 ID가 없으면 최근 대화 8턴을 전달한다. 같은 Run에서 앞선 계정이 실패했을 때는 엔진 종류와 관계없이 그 시도의 오류, 관측 가능한 메시지·도구 결과, 기억과 색인된 work-history 검색 결과를 제한된 길이로 전달한다. 이미 만든 작업 세션과 파일을 확인한 뒤 계속하도록 지시한다.
- 계정 순서는 전역 한 줄이다. 순서 변경 요청의 ID가 현재 목록의 일부여도 받아들이고, 빠진 계정은 기존 상대 순서대로 뒤에 둔다. 이는 목록 조회 이후 계정이 추가된 경우를 수용한다. 중복·존재하지 않는 ID는 400으로 거부하며 로그에는 ID 대신 개수만 기록한다.
