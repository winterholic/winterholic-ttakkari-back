# ADR 0008. 메모·캘린더·한국 공휴일

- 상태: 채택 (2026-10-12)
- 결정자: 사용자("맥 메모/캘린더 앱 대신 따까리 안에", "폰에서 직접 쓰고 에이전트도 읽고 쓰게", "공휴일 자동 반영, API 키 없이")

## 결정

### 저장
- `memos`: `title, body(마크다운), tags(JSONB 배열), category_id, pinned, source(user|agent), rev, deleted_at`. `rev` 는 저장할 때마다 1 오르는 낙관적 잠금 값이다. 편집기 자동 저장이 `rev` 를 같이 보내고, 다르면 409 `conflict` 로 막아 다른 기기·에이전트의 수정을 덮어쓰지 않는다.
- `calendar_events`: `title, description, location, all_day, start_at, end_at, rrule, source, deleted_at`. 모두 `timestamptz` 로 저장하지만 입출력은 **Asia/Seoul 벽시계 문자열**이다(`2026-10-14T09:30`, 종일은 `2026-10-14`). 오프셋이 붙어 오면 KST 로 환산한다. 한국은 DST 가 없어 반복 전개를 벽시계로 해도 어긋나지 않는다.
- 종일 일정은 API 에서 **끝 날짜를 포함**한다(사람·에이전트가 쓰기 쉽게). 저장은 iCal 처럼 끝을 제외한 다음 날 0시다.
- `memo_categories`: `name(유일), color(선택, 토큰 범주 색 키), position`. 메모는 카테고리 0~1개다(폴더처럼 하나만, 여러 갈래 분류는 태그가 맡는다). 카테고리를 지우면 메모는 미분류로 남는다(FK `SET NULL`, 0012).
- 검색은 `ILIKE`(메모는 제목·본문·태그, 일정은 제목·설명·장소)다. 개인 규모라 임베딩은 쓰지 않는다.

### 반복 일정(RRULE): 보류, 재설계 예정
- **2026-10-12 보류.** 반복은 유스케이스 흐름을 다시 설계한 뒤 넣는다. 그때까지 화면·API·MCP 는 `rrule` 을 받지 않는다(보내면 422). `rrule` 컬럼과 전개 코드는 남겨 이미 저장된 반복 일정만 펼쳐 보여 준다(보류 시점 운영 DB 의 반복 일정은 0건). 반복 일정에는 알림을 걸 수 없다. 아래는 보류 전 설계다.
- `python-dateutil`(`holidays` 의존성으로 설치됨)의 `rrulestr` 로 해석하고 **조회 구간만** 펼친다(구간 최대 400일, 일정당 500건). 프런트는 펼쳐진 발생분을 받으므로 규칙을 해석하지 않는다.
- 허용: `FREQ=DAILY|WEEKLY|MONTHLY|YEARLY` 만(초·분·시간 단위는 전개가 폭주해 거부). `UNTIL` 은 KST 벽시계로 정규화하고 날짜만 주면 그날 23:59:59 로 본다. 일정이 한 번도 안 생기는 규칙은 거부한다.
- 한계: 시리즈 전체만 고친다. 특정 회차만 지우기·옮기기(EXDATE·예외 일정)는 아직 없다.

### 한국 공휴일: Python `holidays`(KR), 키 없음
- 설날·추석·부처님오신날(음력), 대체공휴일, 선거일, 과거 임시공휴일을 내장 데이터로 계산한다. 공공데이터포털 특일 정보 API 는 키가 필요해 쓰지 않는다.
- 범위는 2000~2050년. 음력 환산표가 2050년까지라 그 밖은 비운다. 연도별 결과는 프로세스 안에서 캐시하고 서버가 뜰 때 올해 ±5년을 미리 계산한다.
- **한계**: 아직 공고되지 않은 임시공휴일은 패키지가 업데이트되어야 들어온다. 정부 공고 뒤 `uv lock --upgrade-package holidays` 와 재배포가 필요하다. 신규 법정공휴일(2026 노동절·제헌절)도 패키지 버전에 달려 있다.
- 2026·2027년 목록은 `tests/test_planner.py` 에 고정했고 정부 발표와 대조했다.

### 에이전트 도구(MCP `ttakkari`, 모든 Run)
`list_memos` `search_memos` `get_memo` `create_memo` `update_memo` `delete_memo` · `list_events` `create_event` `update_event` `delete_event`.
삭제 안전장치는 `forget`(ADR 0007)과 같은 정책이다.
- 에이전트의 삭제는 `deleted_at` 으로 **보관 처리**(되돌릴 수 있음)이고, **에이전트가 만든 항목만** 지운다. 사용자가 만든 것은 403 `user_owned` 로 앱에서 지우라고 안내한다.
- 사용자 메모의 제목·본문은 덮어쓰지 못하고 `append`(덧붙이기)·태그·고정만 된다. 일정 수정은 허용하되 감사 로그(`calendar.update` 등)를 남긴다.
- 사용자 화면의 삭제는 확인을 거친 완전 삭제다.
- `list_events` 는 같은 구간의 한국 공휴일을 함께 돌려준다("다음 주 일정 정리해 줘").
- `create_event`·`update_event` 는 `reminder` 를 받는다(사용자가 원할 때만 켠다). `update_event(reminder="off")` 는 알림을 끈다. 반복(`rrule`) 인자는 없앴다.

### 알림(2026-10-12 추가)
- 일정마다 고르는 선택 기능이고 기본은 꺼짐이다. 시간 일정은 `at_start`(정시)·`10m`·`30m`·`1h`·`1d`(하루 전), 종일 일정은 `day_9am`(당일 09:00 KST)·`prev_day_9am`(전날 09:00 KST). 종류에 맞지 않는 값은 422.
- 저장할 때 `remind_at`(보낼 시각)을 계산해 둔다. 시각·종일 여부·알림이 바뀌면 다시 계산하고 '안 보냄'으로 되돌린다. 이미 시작한 일정의 지난 알림은 보내지 않는다.
- **발송 방식은 주기 스캔이다.** 서버 lifespan 의 `_reminder_loop` 가 30초마다(`reminder_scan_seconds`) `planner/reminders.send_due()` 를 부른다. APScheduler 같은 별도 스케줄러는 쓰지 않는다. 예약 상태가 DB 에만 있어 재시작해도 잃을 것이 없고, 프로세스가 하나라 잡 저장소를 따로 둘 이유가 없다.
- **중복 방지:** 조건부 `UPDATE … SET reminded_at = now WHERE reminded_at IS NULL AND remind_at <= now … RETURNING id` 로 먼저 차지하고 커밋한 뒤 `notify(PushKind.calendar_reminder, …)` 로 보낸다. 같은 일정은 한 번만 차지되므로 재시작이나 겹친 스캔에도 한 번만 나간다.
- **누락 방지:** 서버가 뜨자마자 한 번 훑어서, 꺼져 있던 사이 지난 알림을 늦게라도 보낸다. 단 `max(시작, 알림 시각) + 1시간`이 지났으면 쓸모가 없어 보내지 않고 건너뛴 것으로 표시한다.
- **남는 틈:** 차지를 커밋한 직후 보내기 전에 프로세스가 죽으면 그 알림은 빠진다(중복보다 누락을 택함). 푸시 서비스가 거절한 경우도 다시 보내지 않는다.
- payload: `title` 은 일정 제목, `body` 는 `10월 14일(수) 10:00 · 10분 후 · 장소`(종일은 `오늘 종일`/`내일 종일`), `url` 은 `/calendar?event=<id>&date=YYYY-MM-DD`(누르면 그 날짜로 가서 일정을 연다), `tag` 는 `event-<id>`.

### 화면 위치
하단 탭은 5개로 두고(채팅·회사·작업 공간·보관함·파일) 메모·캘린더는 사이드바(데스크톱)와 드로어(모바일)의 영역 링크 아래 "메모" "캘린더"로 둔다. 라우트는 `/memos`, `/memos/:id`, `/calendar`. 두 화면은 지연 로딩한다. 메모 상세·편집(`/memos/:id`)과 일정 편집은 가운데 모달(max-height는 dvh 기준, 헤더 고정·본문만 스크롤)로 열고, 바텀시트와 전체 화면 패널은 쓰지 않는다.
