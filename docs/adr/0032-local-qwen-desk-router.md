# ADR 0032. 접수 1순위를 로컬 Qwen3.5-4B 하네스로 바꾼다

- 상태: 채택(2026-10-16)
- 결정자: 사용자("무조건 접수하는 애를 걔로 바꾸자", Qwen 하네스 적용). ADR 0013의 접수 엔진 순서(Luna → Haiku)를 2순위로 내린다. 같은 날 앞선 Shadow Mode 결정(운영 교체 보류)은 이 결정으로 대체된다.

## 근거(2026-10-16 common30-v2, 고정 30문항 x 3회 = 90건, 하네스 확정 뒤 한 번만 측정)
| | hard exact | p50 / p95 |
|---|---:|---:|
| Qwen 4B 기존 프롬프트 | 48/87 = 55.2% | 2421 / 3450ms |
| Qwen 4B + 하네스 v1 | 84/87 = 96.6% | 957 / 1911ms |
| Luna high(기록값) | 76/87 = 87.4% | 4263 / 5573ms |

상세와 한계: experiments/qwen35-router/harness-v1/FINAL-REPORT.md. 합성 문항 기준이고, 하네스는 dev 세트로 튜닝했다. 실로그 분모는 아직 없다.

## 결정
- runs/desk_qwen.py: 모델은 요청 종류(kind)만 고르고 answer/delegate 는 코드가 정한다. 진행·상태 질문은 모델이 작업판/최근 대화에서 인용한 근거가 실제로 있을 때만 직접 답한다. 근거가 없으면 지어내지 않고 기획 세션으로 넘긴다(desk.route 이벤트의 qwen.abstained).
- 기획 세션이 작업판에 있으면 lead_id 를 enum 제약으로 고른다(작업판 밖의 값은 나올 수 없다). 제목은 기존처럼 메시지 첫 줄.
- llama.cpp 는 CPU-only, ctx 8192 로 영구 배치 모델을 쓴다. 최초 구성은 별도 LaunchAgent/127.0.0.1:18080 이었고, 현재 기동·포트·소유권은 아래 운영 연결 개정에 따른다. 연결 실패·시간 초과·잘못된 출력·너무 긴 입력이면 Luna → Haiku 경로로 넘어가고, 실패 뒤 60초는 Qwen 을 건너뛴다. 접수 때문에 메시지가 멈추는 일은 없다(ADR 0013 불변식 유지).
- 끄려면 TTAKKARI_DESK_QWEN_ENABLED=false. 프롬프트는 측정 때와 글자까지 같아야 한다(tests/test_desk_qwen.py 가 SHA256 고정). 바꾸면 다시 측정한다.

## 알려진 한계
- common30-11 같은 "워커/에이전트 상태" 질문이 작업판 일반 질문으로 분류돼 근거 검증을 건너뛰고 답이 지어질 수 있다(측정에서 1문항 x 3회). 개선은 dev 세트를 늘려서 한다.
- 모델 호출이 직접 답변 경로에서 2회, 기획이 있으면 위임 경로에서 2회다. 서버는 --parallel 1 이라 동시 접수는 줄을 선다(시간 초과 20초 뒤 CLI 경로).
- 기획 세션 선택(lead_id)은 신규 dev 26문항에서 위임 대상 23건을 모두 맞혔고 잘못 이어붙인 건 0건이었다. 실로그 검증 전이다.

## 운영 연결 개정 2026-10-16
- 서버 기동 책임을 수동 LaunchAgent 안내에서 backend lifespan 소유의 일반 자식 프로세스로 옮긴다. 접수 첫 호출 때 configured loopback 주소의 healthy 서버를 재사용하고, 없으면 영구 배치된 `llama-server`와 GGUF로 CPU-only 자식을 띄운다. 원격 URL에는 자식을 띄우지 않는다.
- 세대 모드에서 Qwen 자식은 API 슬롯 8791/8792/8793에 대응하는 별도 loopback 포트(18081/18082/18083)를 쓴다. 요청을 맡은 세대만 자기 자식을 종료하고, 외부에서 띄운 서버는 종료하지 않는다. 실패·시간 초과 시 기존 Luna → Haiku 폴백과 60초 건너뛰기를 유지한다.
- 운영 접수의 llama.cpp 응답 usage만 호출별 DB 원장에 저장한다. 평가 호출은 제외하고 prompt/response 본문은 보관하지 않는다. KST 오늘·월요일 시작 주간 사용량은 `/api/accounts/qwen-usage`로 제공한다. 계측 이력이 없던 기간은 수집 시작 시각과 함께 미수집으로 표시한다.

## 개정 2026-10-16 (harness-v2): 사실성 답변은 모든 경로에서 근거가 필요하다
- 결함(확인): common30-11 사후 분석. kind 가 board_overview 로 나오면 근거 검증 없이 answer 가 됐고(무검증 경로), 응답 생성기는 작업판 전체를 보고 자유롭게 써서 "아직도 일하는 중이야" 같은 상태를 지어냈다. 호출 흐름: kind → (board_overview) → 정책 매핑 answer → reply. 근거 검증은 status 에만 있었다.
- 수정: (1) 상태·작업판 질문(status, board_overview)은 근거 줄을 만들고(status=모델 인용을 컨텍스트와 대조, board_overview=코드가 작업판·대화 전체를 근거로 지정) 별도 검증기(대상·범위·시점 3항목, 의심스러우면 no)가 통과시켜야 답한다. (2) 물음표 질문이 둘 이상이면 질문마다 검증한다. (3) 답변 문장은 근거 줄만 보고 쓴다. 사교 응답은 컨텍스트를 보지 않는다. (4) 질문 꼴의 사교 분류는 사교 가드가 한 번 더 확인한다(위장된 상태 질문 차단). (5) 알 수 없는 kind·작업판 밖 lead_id 는 서버가 어겨도 버린다.
- 버전: PROMPT_VERSION=harness-v2, 프롬프트 지문은 tests/test_desk_qwen.py 가 고정. v1 해시는 PROMPTS_V1_SHA256 로 보존(common30-v2 84/87 결과는 v1 의 결과이며 v2 에 적용하지 않는다). v2 는 common30 에서 재측정하지 않았다.
- 검증(합성 dev 4세트, 실모델): 근거 없는 사실성 답변(unsafe) dev4 12 → 1, dev/dev3 0 유지, dev2 1 유지(오타 "배표" 상태 질문). 대가로 직접 답할 수 있던 질문 일부가 기획으로 넘어간다(dev 1 → 5, dev4 4 → 6). 안전 쪽 실패라 허용한다. 자세한 표: experiments/qwen35-router/harness-v1/v2/.
- 알려진 잔여: 물음표 없는 복합 요청("작업판 알려주고 에이전트 상태도 알려줘")은 작업판에 세션 수 필드가 있으면 통과할 수 있다. 오타로 대상을 알아볼 수 없는 상태 질문은 사교로 분류될 수 있다.

## 개정 2026-10-16 (서버 수명주기): 백엔드가 모델 자식 프로세스를 소유한다
- OS 서비스(LaunchAgent) 등록 없이, 백엔드(세대) 프로세스의 lifespan 이 llama-server 를 일반 자식 프로세스로 띄우고 끝낸다(runs/desk_qwen_service.py, 기본 desk_qwen_base_url="").
- 세대마다 자기 loopback 빈 포트(127.0.0.1 만)와 자기 자식을 가진다. 무중단 전환 중 이전 세대가 끝나도 새 세대의 모델은 죽지 않고, 요청은 활성 세대가 자기 자식으로 보낸다. 자식은 소유자만 끝낸다.
- 시작 전 확인: 영구 경로(~/private-resources/service-data/ttakkari-qwen)의 바이너리·모델, 가용 메모리(모델 1.5배와 6GiB 중 큰 값). 준비 표시 전에 분류 호출을 한 번 미리 해 첫 요청 지연(19.8초 → 2.1초)을 없앤다.
- 준비 전·실패 중에는 접수가 Luna/Haiku 로 간다. 자식이 죽거나 health 가 3회 연속 실패하면 백오프(5초~5분)로 다시 띄운다.
- 고아 방지: pid 파일(home/qwen)에 소유자·자식 정보를 남기고, 시작할 때 소유자가 죽은 기록의 자식만 정리한다(서버 경로·포트·시작 시각이 맞을 때만). 살아 있는 다른 세대의 자식과 pid 가 재사용된 남의 프로세스는 건드리지 않는다.
- desk_qwen_base_url 을 지정하면 외부 모드: health 만 확인하고 띄우지도 죽이지도 않는다. 지정한 원격 주소에는 로컬 모델을 켜지 않는다.
- 상태 확인: GET /api/qwen-status (인증 없음, 포트·pid·경로 비공개).


## 개정 2026-10-16 (운영 입력 크기와 우회 관측)
- 운영의 작업판·최근 대화는 4,000자를 넘을 수 있는데, 이전 실모델 시험은 빈 작업판과 60초 제한을 사용했다. 운영 기본 제한은 20초였고 실제 기록에는 시간 초과 후 Codex 처리, 입력 초과 시에는 원인 이벤트 없이 우회하는 경로가 있었다.
- Qwen 전용 컨텍스트는 2,000자 안쪽을 목표로 구성한다. 모든 작업판의 ID·제목·상태를 유지하고 최신 대화를 우선한다. 긴 최근 결과는 필드 전체를 유지하거나 제외하며, 문장 중간을 잘라 근거를 바꾸지 않는다. 사용자 메시지는 자르지 않는다. 핵심 작업판조차 예산에 못 들어가면 기존 입력 제한과 명시적 우회로 처리한다.
- 짧은 입력과 v2 프롬프트·근거 검증·운영 20초 제한은 유지한다. CLI 대체 경로는 기존 전체 컨텍스트를 사용한다.
- 실제 호출 실패는 desk.retry와 경과 시간을 남긴다. 준비 전·쿨다운·입력 초과로 호출하지 않은 경우는 desk.skip에 원인을 남긴다. Qwen route에는 context_chars/context_compacted를 기록하며 원문을 추가 저장하지 않는다.
- 회귀 검증은 운영 크기 컨텍스트의 접수 처리·작업판 보존·큰 입력의 명시적 우회와 실모델 4건이다. 실모델 시험에서도 기본 제한을 덮어쓰지 않는다. 평가 데이터셋과 v1/v2 성능 수치는 이 운영 수정의 결과로 다시 해석하지 않는다.
