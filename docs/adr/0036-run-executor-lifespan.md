# ADR 0036: Run 실행 프로세스와 API 앱 수명 분리(설계)

## 상태
구현 착수(2026-10-21 사용자 명시 지시). 독립 executor 첫 slice는 기능 off로 준비하며,
운영 활성화는 독립 검증 이후다. 소유권·혼합 버전·rollback·미검증 표면은
[실행기 첫 slice](../design/run-executor/first-slice.md)에 기록한다.

초기 상태(2026-10-18)는 “제안, 구현하지 않는다”였다. 3슬롯 무중단 배포에서 장기 Run이 두 세대를
잡고 있으면 후속 배포가 `waiting_slot`에 대기하는 문제를 풀기 위한 설계안이다.

## 배경
- 세대 교체 배포는 슬롯 3개(8791·8792·8793)를 쓴다. 새 릴리스가 후보 슬롯에
  올라가면 이전 세대는 `draining`이 되고, Run·자식 프로세스·HTTP inflight가
  모두 빠지면(`drain_ready`) 감독이 슬롯을 회수한다.
- 2026-10-18 실측: 8792 위의 `claude -p` Run 3개(측정·WBS·조사)가 끝나지 않아
  이전 세대가 draining으로 남고, 그 다음 배포가 밀렸다. 감독을 최신 코드로
  교체해도 슬롯 부족 자체는 해소되지 않는다.
- 근본 원인: Run 엔진 프로세스가 API 앱 프로세스의 자식이다. 8792를 내리면
  Run이 죽고, 살리자면 슬롯을 비우지 못한다. SIGSTOP으로는 DB lease가 풀리지
  않는다. API 수명(릴리스 교체 단위)과 Run 수명(작업 완료 단위)이 묶여 있다.

## 제안
- Run 실행기(executor)를 API 앱과 별도 프로세스(세대와 무관한 상주 1개 또는
  풀)로 분리한다. API 세대는 Run의 라우팅·관찰 지점만 되고, 실제 엔진 자식은
  실행기가 소유한다.
- `RuntimeLease.generation_id`에 실행기 id를 함께 기록한다. drain 판정은
  "이 세대가 소유한 lease가 없음"에서 "이 세대를 경유 중인 Run이 없음"으로
  바뀐다. 실행기는 세대 전환과 무관하게 lease를 끝까지 들고 간다.
- 세대 교체 시 구 세대는 HTTP 유입이 끊기면 즉시 슬롯 회수 대상이 된다.
  진행 중 Run의 SSE·결과 조회는 프록시/신규 세대가 실행기를 대신 조회해
  이어준다(커서·결과는 이미 DB에 있다).
- 실행기 자체의 교체(릴리스 변경)는 Run이 없을 때만, 또는 Run 단위로 점진
  교체한다. 실행기는 상태를 갖지 않고(상태는 전부 DB) 재시작해도 lease를
  다시 읽어 작업을 이어받는 구조로 둔다.

## 위험
- lease·fence(`generation.fence`)가 "같은 프로세스 자식" 가정을 깔고 있다.
  실행기 분리는 소유권 이전 경로를 새로 만들고, 두 주체가 같은 Run에 쓰는
  경쟁을 막아야 한다. 잘못하면 중복 실행·결과 분실이 난다.
- SSE 이어보기·취소·리셋 명령 경로(`RuntimeCommand`)가 세대를 경유한다.
  실행기로 명령을 전달하는 경로를 바꾸면 취소 유실이 생길 수 있다.
- Qwen 상주 서비스·preview 워커·STT 자식 등 세대별 자식 프로세스도 같은
  문제를 공유한다. Run만 떼면 다음 병목이 된다.
- 마이그레이션 없이 시작할 수 없다. `runtime_lease`·`runtime_generation`
  스키마와 활성화 계약(`deploy/generation-contract.json`)의 protocol 상향이
  필요하고, 그 사이 혼합 버전 운영이 필요하다.

## 단계
1. 측정: 장기 Run의 실제 분포(얼마나 자주 두 세대를 잡아두는지)를 ops 로그로
   먼저 확인한다. 드물면 분리보다 "대기上限 + 알림"이 싸다.
2. 읽기 경로 분리: 신규 세대가 구 실행기의 Run 결과를 대신 조회(SSE 커서
   포함)할 수 있게 한다. 쓰기 경로는 그대로.
3. 실행기 추출: 엔진 자식 소유만 별도 프로세스로 옮기고 lease 이중 기록을
   시작한다. drain 판정은 아직 구 기준 유지.
4. drain 판정 전환 + 실행기 점진 교체. 계약 protocol 상향.
5. Qwen·preview·STT 자식의 소속 정리.

## 결과
- 초기 제안 시점에는 선택지 정리였으나, 2026-10-21 사용자 지시로 구현을 진행한다. 1단계 측정 없이는 2단계以降에
  들어가지 않는다.
- 현행 3슬롯 + `waiting_slot` + `supervisor_upgrade_required` 보고 체계를
  유지한다. 이 설계가 구현되기 전까지 장기 Run 경합은 대기·알림으로 다룬다.
