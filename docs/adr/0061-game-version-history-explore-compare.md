# ADR 0061: 버전 이력 탐색·필터·비교 — 새 표 없이 빌드·Run·git 에서 읽는다 (Phase 3, TASK-G32)

- **상태**: 구현됨(2026-10-20). back pytest(게임 관련 152개, 새 테스트 9개)·front vitest(전체 1138개, 새 테스트 13개)·tsc·ESLint(src)·build 통과. Chromium 390x844 에서 합성 데이터로 필터·비교·해 보기 확인. **미검증: 실제 게임 저장소·실제 worker Run 이 쌓인 운영 데이터, 100개 이상 빌드의 성능, iOS Safari·실기기**.
- **설계 정본**: [`docs/design/game-studio.md`](../design/game-studio.md) §7.1(결과 갤러리 비교 패턴), §13.3 G32
- **관련**: ADR 0047(데이터 계약: 새 표를 늘리지 않는다), ADR 0050(활성 빌드·롤백), ADR 0052·0059·0060(피드백 payload)

## 무엇이 이미 있었나

빌드 목록, 이전·최신 두 빌드의 캡처 나란히 보기, 빌드 기록 기반 변경 요약, 되돌리기(G12). 부족한 것은 (1) 빌드가 많아졌을 때 찾는 수단이 없고, (2) 각 버전이 **무슨 요청에서 나왔는지**가 보이지 않으며, (3) 비교가 번들 크기·커밋 해시 수준이라 **무엇이 바뀌었는지**는 알 수 없다는 점이다.

## 설계서와 다르게 정한 점

1. **필터는 "실제 데이터로 가능한 것"만 둔다.** 설계서에는 필터 기준이 없다. 상태(성공·실패·만드는 중), 기간(오늘·7일·30일), 시각 피드백, 검색어(요청문·v번호·커밋·오류)로 한정한다. 별점·태그·작성자는 데이터가 없어 만들지 않는다.
2. **"피드백 유무"를 둘로 나눈다.** `GameFeedback` 표는 모델만 있고 어디에서도 쓰지 않는다(ADR 0047 의 예약 표). 실제로 남아 있는 것은 요청 Run 의 `usage.game` 표식이다. 그래서 *피드백 반영*(이 버전을 만든 요청에 화면 표시·오브젝트·영상 프레임이 붙었다)과 *피드백 받음*(이 버전을 기준으로 피드백이 붙은 요청이 나갔다)으로 정의한다. `GameFeedback` 표를 쓰기 시작하지 않는다.
3. **변경 요약에 소스 변경을 더한다.** 설계서 §7.1 의 "④ 전후비교"는 화면 비교만 말한다. 번들 크기만으로는 변경 내용을 알 수 없어, 두 빌드의 source commit 사이 파일별 증감·커밋 제목(서버가 git 에서 읽음)과 그 사이에 들어온 요청문을 함께 보인다.
4. **플레이 링크 나란히 보기는 하지 않는다.** 390px 폭에서 게임 iframe 두 개를 나란히 두면 각각 170px 안팎이라 조작할 수 없다. 대신 비교 칸마다 "해 보기" 버튼으로 그 빌드를 대화상자에서 한 번에 하나씩 연다. 나란히 비교는 기존 캡처(화면) 쪽이다.

## 결정

### 읽기 전용 API 두 개 (새 표·migration 없음)

| 경로 | 내용 |
|---|---|
| `GET /api/games/{id}/versions?limit=100` | 빌드마다 `is_active`, `produced_by`(만든 요청: 종류·상태·요청문·기준 빌드 순번·피드백 요약), `requests_on`·`feedback_requests_on`. |
| `GET /api/games/{id}/compare?base=&head=` | 두 빌드의 source commit 사이 파일별 증감(최대 40개)·전체 증감·커밋 제목(최대 30개). |

- 요청 연결은 `GameBuild.run_id → Run` 과 `Run.usage.game`(kind·build_id·feedback 개수·repair_attempt·lock_after)이다. 요청문은 worker prompt 의 `[사용자 요청]` 이후 본문을 공백 정리해 200자로 자른다. 최근 500 Run 만 훑는다.
- 요청 정보가 없는 빌드(수동 빌드, 복구 빌드)는 `produced_by=null` 이다. 거짓으로 채우지 않는다.
- `compare` 는 게임 저장소 git **객체만** 읽는다: `diff --numstat -z --no-renames --no-ext-diff --no-textconv`, `log base..head`. 기존 `run_git`(훅 비활성, 사용자·시스템 설정 미사용)을 쓰고, 작업 트리·인덱스·ref 를 바꾸지 않는다. 저장소 안에 `diff.external`·`textconv` 가 설정돼 있어도 실행되지 않는 것을 테스트로 확인한다.
- 읽을 수 없는 경우(커밋 기록 없음, 저장소에 커밋이 없음)는 오류가 아니라 `available=false` 와 사유로 돌려준다. 저장 전 변경이 들어간 빌드(`source_dirty`)는 플래그로 알린다. 경로·커밋 제목은 제어 문자를 지우고 길이를 자른다.
- 다른 게임의 빌드 ID 는 404 `no_build` 다.

### 프론트

- 필터는 이미 받은 목록에서 거른다(서버 재호출 없음). 모바일 폭을 위해 검색창 + "필터" 토글 뒤에 `tk-segmented` 세 줄(상태·기간·시각 피드백)이 열린다. 결과 개수와 "필터 지우기"를 항상 보인다.
- 목록 행에서 "비교에 담기"로 비교 칸을 채운다. 현재 오른쪽(최신)보다 오래된 버전이면 이전 칸, 아니면 최신 칸에 들어가고 이미 담긴 것은 뺀다. 칸이 비면 최신 두 성공 빌드가 기본이다.
- **이전 세대 서버와 공존한다.** Vercel 의 프런트가 백엔드 배포보다 먼저 나갈 수 있다. `/versions`·`/compare` 가 실패하면 빌드 목록과 빌드 기록 요약만 보이고(요청·피드백 필터는 숨김) 안내 문구를 둔다.
- 디자인 시스템: `tk-filterbar`·`tk-segmented--scroll`·`tk-badge`·`tk-dialog`(결과 갤러리 아키타입의 비교·필터 패턴). 색은 토큰만 쓴다.

### 하지 않는 것

- 실제 게임 저장소·운영 데이터 변경, 새 표, 서버 측 필터·페이지네이션(빌드 100개까지는 한 번에 받는다. 넘으면 `limit` 한도 200 이 상한이다).
- 요청문 전문 저장·검색(200자만), 두 버전의 코드 줄 단위 diff 보기(파일 증감까지만).
- 롤백 규칙 변경(되돌리기 정책·잠금 검증은 ADR 0050 그대로).

## 한계

- 요청문은 prompt 머리말 규칙(`[사용자 요청]`)에 의존한다. 규칙이 바뀌면 빈 문자열로 떨어져 요청문만 사라진다(테스트가 잡는다).
- 사용자가 직접 저장소에 커밋한 변경은 "사이의 요청"에 나오지 않는다(소스 변경의 커밋 목록에는 나온다).
- `source_dirty` 빌드와 롤백 후 갈라진 갈래의 커밋 목록은 방향이 맞지 않을 수 있다(파일 증감은 두 커밋 직접 비교).
