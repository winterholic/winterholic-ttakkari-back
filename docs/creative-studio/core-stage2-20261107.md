## 2. 수정 실행 계약과 경계

소유 변경: `src/ttakkari/creative/v2/dispatch.py`, `plans.py`, `engines.py`, `src/ttakkari/api/creative_v2.py`; 신규 core `production_review.py`, 전용 `unit_tests/test_creative_v2_stage2.py` 및 이 문서/증거. producer 3종, quality 2모듈·기존 전용 검사, asset_generation 2파일, frontend 및 다른 담당자의 dirty 변경을 보존했다.

1. `POST production/repair-plan`은 여전히 순수 제안의 영속화다. 응답에 `proposal_sha256`, `plan_revision`, `plan_sha256`, `output_sha256`, `caption_mode`를 추가했다. 제안 hash는 자기 hash 필드를 제외한 전체 제안 JSON에 묶인다.
2. `POST production/repair`는 제안과 정확히 같은 scene/shot/layer 집합에 명시적 문구를 적용한다. 실행 가능한 범위는 기존 업로드 이미지/영상 합성 경로의 captions 텍스트다. 현재 소비하는 `title` 또는 `narration`만 수정할 수 있다. 문구 변경은 결함 해결 판정이 아니라 `applied_needs_approval`이다.
3. `PlanStore.edit(..., caption_updates=...)`는 대상 텍스트와 profile beat만 수정하고, 타 장면의 metadata·타임라인·길이를 보존하며 revision을 올리고 approval을 닫는다. 호출자는 새 revision을 승인한 뒤 기존 production→render를 사용한다. caption_mode를 생략하면 기본 narration으로 돌아가므로 기존 모드를 유지해 다시 dispatch해야 한다.
4. 임의 모션·캐릭터·음성/전환 수리, 음성 자산이 있는 narration 변경, 고정 2D/3D/HyperFrames producer의 caption 수정은 **blocked**다. 마지막 것은 자막 수정 때문에 성공한 producer를 다시 돌리는 것을 막기 위한 제한이다. producer 출력의 독립 재사용 연결을 한 뒤에만 넓힐 수 있다. 원본에 구워진 가짜 문자를 일반적인 caption 교정으로 고친다고 보장하지 않는다.
5. 적용은 기존 `production.lock` flock을 비차단으로 얻는다. 다른 실행자가 점유하거나 segment가 queued/running, asset generation이 queued/running이면 편집하지 않는다. 이것은 **계획별 CPU 작업의 동시 실행 잠금**이며 host GPU resource lease를 획득했다는 증거가 아니다. 이번 지원 경로는 GPU/모델을 호출하지 않는다. GPU/음성 재생성 수리를 우회 구현하지 않았고 기존 managed generation의 인가·generation.lock·ResourceLeaseManager 경로는 그대로다.
6. 변경된 구간은 입력/run_key가 바뀐다. 좋은 구간은 기존 request_render의 hash 확인 재사용 분기로 들어간다. 원본·성공 구간·이전 최종 파일·구 receipt를 삭제하지 않는다. 새 revision에는 구 receipt가 복사되지 않으며, 강제로 복사해도 output/rubric 대조에서 무효다.

적용 감사 기록은 `production.json.repairs[]`에 source revision·새 revision·proposal/output hash·before/after 문구·preserve 목록을 남긴다. plan과 production의 두 파일은 각각 원자 저장되지만 한 DB 트랜잭션은 아니다. 편집 저장 직후 production 감사 저장 전 프로세스가 죽는 crash window의 복구는 이번에 검증하지 않았다. 자동 성공·자동 재승인·모델의 반복 수정 lifecycle은 없다.

## 3. 신뢰된 검수 연결

조사한 기존 경계는 `creative/director.py:create_review`의 `cpu-check/independent=False`와 `registry_data.py:model.multimodal_judge`의 `known_missing=True/integration=none`이다. 둘을 독립 시청 검수로 승격하지 않았다. 이는 **이 작업 트리 조사**이며 현재 운영 배포의 capability 판정이 아니다.

`production_review.EVALUATOR_BINDING`은 기본 None이다. 서버 bootstrap/신뢰된 executor 코드만 `EvaluatorBinding(id, version, source, independent, execute)`를 지정할 수 있다. HTTP는 revision만 받고, evaluator 설치·receipt 업로드·independent 플래그 입력 API는 없다. 실제 하네스가 연결되면 `execute(package, payloads)`가 기존 quality_worker의 MP4/PNG/WAV 바이트를 받아 semantic 또는 viewing receipt를 반환해야 한다.

수용 순서는 다음과 같다.

- 현재 승인 revision·출력·rubric·assets 지문 확인 → 실제 평가 package 준비·바이트 전달 → callable 실행.
- 응답 evaluator의 자칭 id/source/independent는 server binding 값으로 대체한다. 파일의 path·sha뿐 아니라 source hash·kind·시각도 실제 전달 manifest와 대조한다. video를 audio라고 바꾼 응답은 거부한다.
- 실행 후 production 잠금을 다시 얻어 revision·출력·rubric·assets가 그대로인지 대조한다. 평가 중 편집되거나 파일이 변하면 저장하지 않는다.
- `quality_evidence[]`와 `quality_attestations[]`에 receipt SHA, output SHA, rubric SHA, evidence 목록 hash, input manifest hash, execution ID를 함께 기록한다. `_assemble`도 attested receipt만 pure evaluator에 전달한다.
- `quality.evaluate_production`의 기존 기준별 모달리티·전체 장면 범위·uncertainty 검사를 그대로 사용한다. rubric hash 일치는 생성 시각의 독립 증명이 아니다.

이 hash들은 **무결성 결합**이다. 신원 신뢰는 클라이언트가 쓸 수 없는 server binding/production 저장 경계에서 온다. 원격 서명·인증 프로토콜을 새로 구현한 것이 아니며, 로컬 저장소를 악의적으로 쓸 수 있는 서버 코드/운영자를 방어하는 계약도 아니다. 참조 문헌 파일의 임의 추가·외부 증거 수입은 현재 manifest 허용 목록에 없으므로 별도 연결이 필요하다.

독립 평가를 실행하지 않은 실제 전후 실험의 결과는 machine=pass, semantic=unknown, viewing=unknown, overall=unknown이며 `/review`는 `not_connected`다. 전용 테스트의 `contract-fixture`·`self-review-fixture` callable은 통합/거부 반례만 입증한다. 실제 독립 GPT/Claude/사람 평가나 청취 증거가 아니다.

## 5. UI 소유자에게 넘기는 최소 API

기본 경로는 `/api/creative/v2/plans/{pid}`다. 아래 POST와 revisions 조회는 기존 `User` 인증이 필요하다. URL 발급은 owner 인증을 요구하고, 미디어 GET은 만료되는 download JWT의 plan/revision/result와 출력 hash를 대조한다. 파일 경로를 클라이언트 입력으로 받지 않는다.

| 요청 | body / 응답의 핵심 |
|---|---|
| 기존 `GET /production` | 현재 quality_report·repair_plan·review_execution·repairs·history, segments의 run_key/output_sha256/result_id. `state=succeeded`는 기계 QA 호환 상태이며 의미 품질 합격이 아니다. |
| `POST /production/repair-plan` | `{revision, defects:[{scene_id,shot_id?,code,layer}]}` → actions·blocked·invalidate·preserve·proposal_sha256. |
| `POST /production/repair` | `{revision,proposal_sha256,updates:[{scene_id,shot_id?,layer:"captions",field:"title"|"narration",text}]}` → `applied_needs_approval`, 새 revision, changes.before/after·보존 목록. 미지원은 `blocked`, stale/잠금/인가 문제는 오류이며 적용 없음. |
