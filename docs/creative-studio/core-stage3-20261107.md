## 2. 재사용한 lifecycle과 신뢰 경계

기존 `run_extraction`은 Qwen intent 추출을 queue_run에 넣고 개인 worker session·Run metadata·구조 검증·재개를 처리한다. 새 storyboard도 **같은 queue_run**과 models.Run/ChatSession, 계정 라우팅·generation fencing을 사용한다. qwen-local/codex만 허용하고 모델은 기존 engine_models allowlist 및 worker 기본 모델을 사용한다. 새 인증·토큰·계정 설정·모델 서버를 만들지 않았다.

입력은 자유 brief와 `{id, locator, text}` 출처 목록이다. 출처를 URL/경로로 자동 열지 않는다. 모델의 `knowledge`는 source_id·연속 quote·application을 반환하고, 각 장면은 인용한 source_id를 참조해야 한다. 이것은 **주어진 원문과의 인용 일치 검사**이며 출처 자체의 진실성·전문가 독립 검증·자동 RAG 검색이 아니다.

출력에는 summary/catalog_ids/knowledge/scenes가 필요하다. scene의 title/narration/seconds/strategy/preset/rationale/alternatives와 1개 shot의 action/layers/required_capabilities를 기존 엄격한 모델로 검증한다. 알려지지 않은 필드·능력, 중복 scene/shot ID, 출처 없는 quote, 대안 누락·동일 대안, 빈 layer는 거부한다. 모델은 reviewed·run/model provenance·사용자 승인을 만들 수 없다.

성공 Run의 출력 hash를 명시적으로 검토한 `accept`만 ProductionDirection을 만든다. `run_id`, `output_sha256`, 실제 선택 모델, 출처 인용과 대안의 근거를 유지한다. 기존 build_plan의 검토 게이트를 통과시키기 위해 **명시적 hash 검토 후** intent.extraction을 user_structured로 전환하지만 선택 source는 llm_inferred이며, director에는 LLM 출처와 Run 지문을 남긴다. `reviewed=True`는 이 수용 단계의 검토 표지이며 plan approval을 대신하지 않는다. 생성·편집된 계획은 승인 없음/render_gate=false 상태로 나온다.

새 계획 ID는 Run ID와 출력 SHA에 결정적으로 묶어 정상 순차 재전달이 새 계획을 중복 생성하지 않도록 했다. 기존 계획 편집은 revision과 카탈로그 일치를 요구하며 레시피를 몰래 바꾸지 않는다. plans create→edit는 한 DB transaction이 아니므로 중간 프로세스 종료로 미승인 draft가 남는 crash window는 미검증이다. 동시 최초 start의 전역 request-key 경합도 실 DB 부하로 검증하지 않았다. 큐 상태의 단순 등록을 exactly-once 모델 추론 보증으로 확대하지 않는다.

`read`는 queued/running/failed/cancelled/interrupted를 기존 Run 상태로 반환한다. 모델 실행이 succeeded여도 파싱 실패면 phase=invalid_output이고 계획으로 승격하지 않는다. 유효 출력은 completed_needs_review다. `resume`는 terminal Run에서만 같은 출처 입력으로 새 Run을 queue_run에 넣고 resumed_from을 기록한다. cancel은 기존 api.sessions.cancel_run/RunManager를 그대로 호출한다. 실제 엔진 취소·실패·재개 전체 조합은 이번 실제 모델 호출에서 재연하지 않았고 전용 fixture 반례와 기존 구현으로 확인했다.

## 3. 기존 durable consumer에 연결한 렌더 계약

`queued_work.py`는 큐가 아니라 drain/inflight 추적기다. 기존 durable 데이터는 production.json이며 asset_worker가 queued asset_generations를 처리한다. 새 렌더도 **기존 dispatch 레코드의 render_request 한 개**를 사용한다. 새 큐 테이블·데몬·별도 인증·polling 서비스를 만들지 않았다. 기존 generation_service._creative_assets/maintenance_jobs/start_legacy_queued_consumers 경로가 asset_worker를 부르고, 자산 대기분 이후 렌더 요청을 소비한다.

- enqueue는 현재 승인 plan id/revision, dispatch 존재, 자산 완전성·실제 파일 SHA를 확인한다. key에는 승인 계획 지문·revision·caption_mode·asset manifest·compositor version이 들어간다. 같은 key의 기본 재전달은 동일 요청을 반환한다.
- 소비자는 plan별 render-consumer.lock flock을 얻고 production.lock 아래 queued→running을 기록한다. 승인 snapshot·현재 revision·manifest·파일 SHA를 다시 대조한 뒤 기존 dispatch.request_render를 호출한다. 같은 ProductionStore에 결과·오류·시각·lease ID를 남긴다. 다른 프로세스가 잠금을 점유하면 queued 그대로다.
- queued_work.delegated인 API는 새 render consumer가 일을 실행하지 않는다. remote API의 director dispatch는 순수 Style DNA/spec/limits 검증을 유지하면서 runtime preflight만 executor로 미룬다. `request_render`의 기존 remote API native 실행 거부도 유지했다.
- 새 소비 표면은 director의 업로드 이미지/영상 slideshow·기존 영상 playback뿐이다. 고정 2D 신규 제작·HyperFrames·Blender는 이 소비 경로에서 blocked다. legacy 비감독 V1은 기존 Studio render queue를 그대로 쓴다. Kafka를 슬라이드쇼로 자동 대체하지 않는다.
- cancel은 queued만 cancelled로 바꾼다. 이미 running이면 중단했다고 거짓 표시하지 않고 거부한다. 현재는 실행 중 FFmpeg의 안전한 중단/고아 running 자동 복구가 없다. running 기록은 자동 재전달하지 않으며 명시적 조정이 필요하다. terminal 실패/취소는 같은 승인 입력에서 retry=true로 새 요청을 남길 수 있다. 성공 요청의 같은 key는 재실행하지 않는다.
- 새 CPU 작업의 동시 실행 제어는 파일 잠금이다. host GPU ResourceLeaseManager를 얻었다는 증거가 아니다. 이번 경로는 GPU·Comfy·TTS·새 2D producer를 호출하지 않으며 그 기존 자원 lease·인가 경로도 우회 구현하지 않았다.

원격 API는 접수·조회만 하고 executor는 공유된 기존 PlanStore/ProductionStore 경로에서 실행해야 한다. **운영 원격 storage/프로세스 경로의 연결·배포 확인은 남았다.** 코드 연결/로컬 함수 실실행/운영 서비스 실실행을 구분한다.

최종 MP4는 9.03초, SHA `9545d35f1b747e08c8df292e71ca7630e93b3503b81bee32f0f4a2bad797e3cd`, 420,459 bytes. 세 성공 segment의 run_key·SHA, 자산 구간/해시, 원문 FFmpeg 명령, 승인 snapshot은 [실제 결과](core-stage3-evidence-20261107/journey-result.json)와 ZIP에 있다. 상단 crop의 0.3/0.7초 frame MD5가 달라 원본 움직임이 정지화되지 않은 것을 확인했다. 정지 프레임 1장을 직접 열었지만 독립 전체 시청/청취 검수가 아니다. machine=pass, semantic/viewing/overall=unknown이다.

## 5. API와 UI 연결

모든 새 도메인 endpoint는 기존 `User` 인증을 요구한다. 클라이언트는 raw result_text나 evaluator 독립성을 올려 통과시킬 수 없다. 새 큐 인증·토큰을 만들지 않았다. 현재 운영 backend는 이 API가 없는 이전 배포다.

| 경로 | 입력·상태·오류 |
|---|---|
| `GET /api/creative/v2/storyboard/contract` | request/output JSON Schema, review_required/approval_required_after_accept. |
| `POST /storyboard/runs` | `{brief,sources:[{id,locator,text}],engine:"qwen-local"|"codex",model?}`; Idempotency-Key 지원, 202 session_id/run_id/status. 엔진/모델 미허용·Qwen 비준비 503. |
| `GET /storyboard/runs/{rid}` | phase, status/error, storyboard, sources, output_sha256, review_required, resumed_from. 유효 출력도 미승인. |
| `POST /storyboard/runs/{rid}/resume` | 기존 terminal 상태만 새 Run 생성. 실행 중 재개 409. 기존 Run queue/계정 정책 유지. |
| `POST /storyboard/runs/{rid}/cancel` | 기존 session API/RunManager 취소 위임. 해당 storyboard 출처 검증 후만 호출. |
| `POST /storyboard/runs/{rid}/adopt` | 위 request 본문과 **실제 DB Run의 engine·완전 일치 prompt**를 대조해 기존 일반 Run을 수입한다. result_text는 DB에서만 읽는다. 불일치 409. |
| `POST /storyboard/runs/{rid}/accept` | `{reviewed_output_sha256,plan_id?,revision?}`; succeeded와 현재 출력 hash 검증. SHA/구조/대상 충돌은 422/409. 계획은 미승인으로 반환하며 기존 plan 승인 필요. |
| 기존 `POST /plans/{pid}/approve` | `{revision}`. storyboard 검토와 렌더 승인 분리. |

| 기존 `POST /plans/{pid}/production/render` | `{revision,retry?:false}`. remote API/director는 승인된 요청만 durable enqueue, 202 production view의 render_request/status와 state=queued. 지원 밖 producer는 422 executor_surface_blocked. 로컬 호출·기존 legacy V1은 기존 경로 유지. |

| 기존 `GET /plans/{pid}/production` | render_request의 queued/running/succeeded/failed/blocked/cancelled·error·lease ID와 기존 scene/segment/quality 상태. |

`/storyboard/*`의 전체 prefix는 `/api/creative/v2`다. 이벤트/SSE는 기존 `/api/runs/{rid}/events`·`stream`을 재사용한다. UI는 자유 brief/출처 입력→Run 상태/구조 오류→출처·장면·샷·대안 검토→SHA accept→기존 plan 승인→dispatch/render→queue/lease/결과·quality unknown을 연결해야 한다. Stage2의 result-link/revision/부분 수정 계약은 유지한다. frontend 파일을 고치거나 실제 UI 로그인·제작 여정을 실행하지 않았다.

- 이 보고서 공유 ID는 [공유 색인](core-stage3-evidence-20261107/shared-files.json)에 추가한다. 산출물은 이번 Run outbox에서만 공유한다.

하지 않음: 새 도메인 HTTP start/adopt/accept/resume의 운영 실여정과 운영 원격 executor 실소비 — 운영 revision이 이전이며 이번 카드가 배포를 금지한다. 새 supervisor의 자동 반복 개선/고아 running 복구·실행 중 CPU 렌더 취소·동시 start DB 경합·worker crash 모든 구간은 미검증이다. 실제 독립 의미·시청·청취 평가, UI 실제 여정, A/C 실제 렌더, commit/push/배포·감사 전달도 하지 않았다. 이 미완료를 등록·단위검사·로컬 MP4 성공으로 대체하지 않는다.

다음 후보: 총괄이 변경·DB/프로토콜/스토리지 경계를 검토해 통합 배포한 뒤 owner 인증으로 새 storyboard lifecycle을 실행하고 executor role/storage에서 durable 요청을 소비한다. 그 다음 UI 실제 여정 및 독립 평가·감사를 진행한다. 이번 새 범위에 필요하지 않은 producer/quality/frontend의 발견은 수정하지 않았다.
