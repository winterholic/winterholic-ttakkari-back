# 수집 관리 전면 리팩토링 설계 (2026-11-05)

상태: 구현 완료(P0~P3 일부), 운영 배포 대기. 아래 §6 에 구현 결과와 설계 변경을 적는다. 근거는 사용자 지시문 원문과 2026-11-05 운영 API 실측이다.

## 1. 원래 의도 (사용자 말)

"디자인시스템 레퍼런스를 싹 다 긁어와" 한 줄이면, 토스·네이버·카본 같은 디자인 시스템의 오픈소스·철학·위키, 그 엔지니어와 디자이너가 기술 블로그·기사·인터뷰에서 한 말까지 최대한 찾아 가져온다. 가져오는 동안 가벼운 모델이 쓰레기를 판별한다. 통과한 것은 지식 도서관에 온톨로지 기반 RAG로 저장한다. UI는 이 모든 과정을 보여줘야 한다.

UI에 반드시 보여야 하는 것은 세 가지다.

1. 사용자가 준 지시문 원문.
2. 지시문이 요구한 절차와 수집 관리 자체의 절차를 얼마나 따르고 있는가.
3. 단계별로 무엇이 들어오고, 무엇이 버려지고, 무엇이 막혔는가.

## 2. 현재 상태 (실측)

| 항목 | 사실 |
|---|---|
| 임무 | 운영에 1건(디자인 시스템 백과사전). 6회 재실행 모두 `mission_prepare` 단계 `attempts_exhausted`. 수집·적재 0건 |
| 에러 | 작업 error 에 type(`CollectorContractError`)만 남고 message 가 없다. 원인을 DB 에서 알 수 없다 |
| 카운터 | 작업 6건 실패인데 `counts.failed=0`. 카운터는 자료 단위라 작업 실패가 안 잡힌다 |
| 출처 관문 | 후보 28개 중 16개가 `source_policy_required`. 미리 등록된 출처 정책이 없으면 URL 을 가져오지 않는다(`collector/missions.py` 의 정책 탐색). 자율 수집(주제만 주기)과 충돌 |
| 온톨로지 | KB `entities/assertions/relations` 전부 0. 임무 `knowledge_processing` 은 `storage: pending, semantic: unverified` |
| UI | 지시문(`goal`) 미표시, 카운터 8개와 다시 실행·주기 설정뿐. 절차 이행 여부 없음 |

## 3. 목표 모델

```
지시문 원문(보존·표시)
  → 요구 체크리스트(지시문에서 추출: 대상, 분야, 규칙, 금지)
  → 파이프라인: 탐색 → 획득 → 추출 → 판별 → 적재 → 온톨로지
  → 모든 단계가 mission_events(append-only)에 기록
  → UI 는 mission_events 와 체크리스트 평가만 읽는다
```

### 3.1 mission_events (새 append-only 로그)

`seq`, `mission_id`, `run_seq`, `stage`, `kind`(started/progress/item/discard/block/error/done), `subject`(URL·질의·문서 id), `payload`(JSON), `at`. 단계 코드는 상태를 바꾸면서 같은 트랜잭션에서 이벤트를 쓴다. 카운터와 UI 는 이 로그에서 파생한다. 작업 실패도 message 와 함께 `error` 이벤트로 남긴다.

### 3.2 요구 체크리스트

지시문을 한 번 구조화한다. 결과는 임무에 저장하고 사용자가 고칠 수 있다.

- 대상: 지시문이 이름으로 든 디자인 시스템·기관(예: IBM Carbon, Material, Apple HIG, NN/g, WCAG, GOV.UK).
- 분야: Typography, Spacing, Layout, Table, Form, Accessibility 등.
- 규칙: "근거 없는 수치를 정답처럼 저장하지 마", "공식 표준·연구·벤더 권장·경험칙 구분", "무관한 페이지 무제한 크롤링 금지", "실패와 누락을 기록하고 재시도".
- 각 항목의 상태는 수집 결과에서 결정적으로 계산한다(미착수 / 진행 / 충족 / 부족). LLM 이 "충족"을 선언하게 하지 않는다.

### 3.3 출처 관문

`source_policy_required` 로 막는 방식을 없앤다. 임무가 찾은 출처는 robots·접근 정책·도메인 단위 자동 정책으로 처리하고, 어떤 근거로 허용했는지 이벤트에 남긴다. 원문 전체 복제가 아니라 출처를 보존한 구조화 발췌 저장이 기본이다(지시문 6번). 접근 불가·로그인 필요·robots 금지는 `block` 이벤트로 남기고 사용자 개입 없이 다음 출처로 진행한다.

### 3.4 판별 감사

경량 모델이 버린 자료는 사유와 축별 점수와 함께 `discard` 이벤트로 남고, UI 에서 열람·복구할 수 있다. 검증되지 않은 모델 점수로 영구 삭제하지 않는다.

### 3.5 온톨로지

지식 도서관 소관이며 별도 단계로 분리한다. 최소 모델: 엔티티(디자인 시스템, 컴포넌트, 토큰, 원칙), 주장(수치·조건·예외), 근거 등급(공식 표준 / 연구 / 벤더 권장 / 경험칙), 출처 관계. 상충하는 주장은 조건과 출처를 구분해 보존한다. 적재 완료 판정은 원문 저장이 아니라 이 단계의 통과로 한다.

## 4. 단계와 인수 기준

| 단계 | 내용 | 인수(실제 동작 증거) |
|---|---|---|
| P0 | 실패 원인 노출: 작업 error 에 message·traceback 요약 저장, 카운터에 작업 실패 포함 | 운영 임무 재실행 시 원인이 화면에 보인다 |
| P1 | mission_events 도입과 모든 단계의 기록 | 임무 1건의 이벤트 로그 조회 API |
| P2 | 출처 관문 제거와 자동 정책, 수집이 실제로 도는 것 | 운영 임무가 N 페이지를 실제 획득·판별·적재 |
| P3 | 지시문 패널·체크리스트·파이프라인 뷰·판별 감사 UI | 모바일·데스크톱 실제 화면 |
| P4 | 온톨로지 적재 | 엔티티·주장·관계 건수와 근거 있는 질의 답변 |

각 단계는 독립 커밋으로 main 에 합친다. 배포는 단계마다 사용자 확인 후 한다.

## 5. 하지 않는 것

- 수집 플랫폼을 별도 서버·큐로 분리하지 않는다(모듈형 모놀리스 유지).
- 지식 도서관 검색·정본 기능을 수집 쪽에 중복 구현하지 않는다.
- 일부 수집을 전체 완료로 선언하지 않는다. 완료는 체크리스트 평가와 적재 증거로 한다.

## 6. 구현 결과와 설계 변경 (2026-11-05)

- 실측으로 드러난 진짜 원인: 계획기가 지시문 문장 키워드를 검색어로 써서 지시문에 이름이 나온 31개 대상이 한 번도 검색되지 않았다.
  `collector/catalog.py` 가 검증한 공식 루트·14개 분야·깨끗한 질의를 만들고 대상·분야별 커버리지를 계산한다.
- `mission_events` 테이블은 만들지 않았다. 진행 기록은 작업·항목·전달·KB 파이프라인 행에서 파생한다(`collector/trace.py`, `GET /missions/{id}/trace`).
  별도 기록은 저장된 상태와 어긋날 수 있고 수집 경로마다 계측을 넣어야 해서 기각했다.
- 출처 관문은 기록되는 호스트 단위 자동 정책으로 바꿨다(`ensure_auto_policy`). basis 에 라이선스 검토가 아님을 명시하고 export·train 은 unknown 으로 둔다.
- 라이브 실행(실제 인터넷, 임시 DB)에서 찾아 고친 것: 검색 봇 차단(6초 간격), 이어받기 시드 50개 초과로 31건 격리, 보류 주소 189건이 기록을 도배.
- 온톨로지(P4)는 새로 만들지 않았다. KB 의 6단계 자동 지식화 파이프라인이 이미 있고, trace 가 문서별 단계 진행을 보여준다. 운영에서의 추출 결과는 배포 후 확인한다.
