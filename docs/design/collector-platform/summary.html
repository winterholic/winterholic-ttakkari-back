수집은 범용으로,
판정은 근거와 예산 안에서

기존 실행 기반 위에 독립 수집 플랫폼과 ML 품질 평가를 쌓는 3단계 실행 설계

2026-10-20 · 설계/PMS 납품제품 구현·학습·배포 미실행

핵심 결정

수집 플랫폼은 지식 도서관과 독립된 모듈로 둡니다. 표준 envelope로 교환하고, 기존 PostgreSQL·generation 실행기·PMS·저장소를 재사용합니다.

별도 서버나 새 큐 제품을 추가하지 않습니다. 독립 관리 화면은 /collect, 지식 저장/검색은 선택적 adapter를 통해 연결합니다.

1. 무엇을 만들 것인가

01 · 탐색과 획득

API/feed/공식 문서/파일 → 출처별 robots·권리·증분 cursor → 안전 fetch

02 · 표준화와 품질

원본 SHA·본문·전처리 버전 → 중복 후보 → 규칙·로컬 ML → 고정 예산 teacher

03 · 결과와 소비

IngestionEnvelope 1.0.0 → delivery receipt → export / knowledge adapter

공통 기반

generation periodic/consume/work + PostgreSQL durable job / 원자 예산 예약 / scope / audit / 회수 가능한 보류

Run 전용 lease는 수집 job ID에 직접 쓰지 않습니다. 기존 generation 작업 lock을 쓰면서 job 행에 owner generation과 attempt token을 두고 stale commit을 막습니다.

2. 수집량과 LLM 비용을 분리

단위제안 절대 한도강제 방식
일별 공용60,000 tokens · 20 calls · USD 1모든 job·teacher·judge·합성·retry 합산
job별12,000 tokens · 4 calls · USD .20일별 bucket과 함께 DB 원자 선예약
표본일 최대 12문서고정 reservoir + 남은 예산 안에서 선택

상한은 운영 확정값이 아닌 초기 제안입니다. 사용량 미확정은 예약을 유지하고, reasoning/output 상한을 강제할 수 없는 엔진은 teacher 경로를 끕니다. 내용 hash·모델·전처리·정책·질의별 캐시로 재판정을 줄입니다.

3. 점수 하나로 모든 것을 확정하지 않기

교육가치·실용성·스팸·사실성·관련성은 별개입니다. 검색 nDCG/Recall은 질의·코퍼스 수준의 별도 평가입니다. 낮은 점수 문서는 보류하고 표본 감사로 놓친 고품질 문서를 회수합니다.

이전 조사에서 바로잡은 점

27건은 편의표본이며 독립 gold가 아닙니다. PlusPlus는 후보로 유지합니다. mfwedu raw logit을 유지하고 sigmoid를 보정된 품질 확률로 쓰지 않습니다. 과거 검색/원장 수치는 당시 스냅샷입니다.

실제/합성·teacher/독립 AI/사람 라벨을 구분합니다. 사람 확인이 없으면 자동 reference baseline으로 보고하고 human validation은 미실행으로 남깁니다. 출처·원전·번역·합성 family와 시점별 누출을 막은 split에서 calibration·ablation·false-negative·CPU/RSS·절대 비용을 함께 평가합니다.

BEIR/MS MARCO는 검색 관련성 비교에 사용합니다. 사실성은 원출처·시점·버전별 주장 근거로 별도 검증합니다. BEIR 공식 자료 · MS MARCO 공식 자료

4. 세 단계와 실제 PMS

  1. S1 · 증거와 실행 설계 — 3건

    조사 정정 → schema·아키텍처·평가·WBS/PMS. 이번 worker 범위.

  2. S2 · 수집 플랫폼 — 11건

    소유권/환경 → 계약·멱등 → generation/cursor → safe fetch·정규화·예산 → 관리 UI/API → adapter → 복구·파일럿.

  3. S3 · ML·검증·개선 — 11건

    라벨/split → 기준선·공개 모델 → teacher/student → calibration·ablation → 독립 holdout·검색 → shadow/rollback·재학습.

5. 첫 구현 패키지

CP-S2-01 · strict 계약 검증과 멱등 등록
48d0a2b4-09f5-47ab-a6ac-d86a92c249a5

동일한 요청 10개를 병렬 제출해도 job은 1행이어야 합니다. 다른 payload는 409, scope 교차와 text hash 변조는 거부합니다. 첫 패키지는 네트워크·LLM·knowledge write 없이 끝냅니다.

예정 파일은 collector/contracts.py, collector/intake.py, 전용 모델·additive migration과 계약/등록 테스트입니다. 기존 dirty 파일과 미추적 kb 파일은 다른 작업 소유이므로 변경하지 않습니다.

독립 검증 보완(10/20): envelope의 tenant·scope·principal 값은 믿지 않고 인증 주체에서 산출해 다르면 403으로 거부합니다. 멱등 비교는 RFC 8785 JCS에서 recorded_at만 빼고 SHA-256으로 합니다. intake/migration은 CP-S2-00 확인 뒤 진행합니다. 현재 PMS 상태는 doing 10%입니다. 상세는 intake-binding.md.

6. 검증과 남은 경계

이번 실행 증거

JSON Schema 2종 meta-validation · fixture 18건: 양성 4 / 음성 14. PMS 25건의 ID·소유 역할·의존 UUID readback 대조. 전체 receipt는 패키지에 포함합니다.

아직 실행하지 않은 것

제품 코드·DB migration 적용·실제 LLM 예산/SSRF/lease 동작·모델 학습·human gold·현재 배포 runtime/DB 동일성·운영 성능·배포는 미실행입니다. 문서 fixture 통과는 운영 보장이 아닙니다.

블로커는 어느 작업에 영향을 주는가

back 소유권/migration graph 확인은 구현 착수 전 필요합니다. front 발산은 UI 단계, kb ACL/visibility/parser 계약과 legacy P0 gate는 knowledge sink만 막습니다. collector와 export는 독립적으로 진행할 수 있습니다. bounded teacher가 없으면 LLM off 경로를 유지합니다.
