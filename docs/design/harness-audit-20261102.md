# 하네스 점검 2026-11-02

2026-10-19 이후 작업자 Run 2365건(작업 세션 870개)과 코드를 대조한 결과다. 수치는 운영 API(`/api/sessions`, `/api/sessions/{id}/runs`)에서 2026-11-02 새벽에 직접 집계했다. 집계 스크립트는 저장하지 않았으므로 재현하려면 같은 API를 다시 훑어야 한다(확인 필요).

## 한 줄 결론

일을 못 하는 원인은 모델 하나가 아니라 구조 네 가지다. 작업자에게 완료 계약이 없었고, lead 상시 지침이 길고 서로 모순됐으며, 완료 주장을 검증하는 장치가 일부 모델에만 걸려 있었고, 배포가 막혀 고친 것이 운영에 반영되지 않았다.

## 근거

### 1. 완료 주장을 믿을 수 없다
- 독립 검증이 끝난 Run 중 `false_completion=true`가 216건, `false`가 206건이다. 검증된 완료의 절반이 가짜 완료였다.
- 엔진별로는 antigravity 102/136(75%), claude 31/62(50%), codex 60/157(38%), muse 20/57(35%)다. Claude도 낮지 않다.
- 한계: 검증은 무작위가 아니라 Flash·Muse·Qwen 결과나 lead가 의심한 작업에만 걸렸다. 엔진 간 우열 근거로 쓰면 안 된다. "가짜 완료가 흔하다"의 근거로만 쓴다.
- Codex 1347건, Claude 419건은 `verification_required=false`라 한 번도 검증되지 않았다. `needs_independent_verification`이 Flash·Muse 모델의 general/routine에만 참을 돌려주기 때문이다(`runs/worker_routing.py`).

### 2. 작업자에게 완료 계약이 없었다
- 작업자 역할 지침(`worker.md`)이 저장소에도 `~/.ttakkari/harness`에도 없었다. 작업자가 받은 것은 `AGENT_NOTE`(MCP·배포 정책 중심)와 공통 지침뿐이다.
- Codex는 `~/.codex/AGENTS.md`도 함께 읽는다. 거기에는 "토론이 기본", "요청 범위에서 멈춤", "막히면 이유를 말하고 대안 제시", "실행 못 하면 `미실행: 이유`"가 있다. 대화형 규칙이라 무인 작업자에게는 일찍 멈추는 출구가 된다. 이것이 사용자가 본 증상의 원인인지는 확인 필요(추정).
- 조치: `WORKER_DEFAULT`를 추가했다. 끝까지 수행, 마지막 메시지 첫 줄 `상태: 완료|부분|막힘`, 항목별 결과, 실행 증거, 범위 밖 발견은 보고만. 전역 규칙보다 우선한다고 명시했다. `~/.ttakkari/harness/worker.md`를 저장하면 그 파일이 우선한다.

### 3. lead 상시 지침이 길고 서로 모순된다
- 2026-11-02 원격 `main` 기준 lead 기본 지침은 약 29K자였다(추정, 상수 길이 합산). 변경 후 약 23K자다. 작업자는 약 10.8K자에서 약 9.8K자다.
- 가장 큰 덩어리는 라우팅 노트(약 9.8K자)였다. Qwen·Muse·Copilot 세부 규칙은 `account_usage`가 이미 돌려주는 정보라 요약만 남겼다.
- 모순: `~/.ttakkari/harness/lead.md`는 "engine/model/effort를 명시하고 auto의 공급자 우선순위로 대신하지 않는다"고 하고, 라우팅 노트는 "engine=auto와 task_type을 쓰고 model/effort는 생략한다"고 한다. 라우팅 노트가 우선한다고 적혀 있지만 lead는 둘을 모두 읽는다. `lead.md`는 사용자 소유 파일이라 고치지 않았다. 사용자가 정할 일이다.
- lead가 작업자에게 보낸 프롬프트 중 200자 초과 2326건의 41%(965건)가 공백 비율 8% 미만이다. 예: "앞선동일인프라후속에합칠...". 10/25부터 늘어 10/29에 정점이었다. 원인은 찾지 못했다(확인 필요). 작업자가 지시를 잘못 읽을 위험이 있어 위임 명세에 "공백 있는 평문, 자기완결"을 넣었다.

### 4. 계획 비용
- 작업자 Run 2365건 중 64%(1504건)가 첫 Run 이후의 후속이다. 기획 하나에 작업자가 중앙값 6개, Run이 중앙값 13개다.
- 최대 사례: "레그나 iOS 실사용 모델 연구" 작업자 200개·Run 389건, "레그나 iOS 메모리 경합 실측 연구" 작업자 75개·Run 326건. 한 세션에 Run 56건이 쌓인 "중단 복구" 건도 있다.
- 작업자 세션의 task_type은 verification이 388개로 general 389개와 비슷하다. 검증 작업자가 전체의 절반이다. 필요한 검증인지, 중복인지는 확인 필요.
- 조치: lead 위임 명세에 완료 기준(확인 가능한 항목), 검증 명령, 단위 분할, "후속 두 번에 진전 없으면 재계획"을 넣었다. 원격 `main`에는 이미 `PLANNING_CONTRACT`와 `manage_work`(10/25 커밋 fb746022)가 있어 중복 규칙은 쓰지 않았다.

### 5. 배포가 막혀 있었다
- 운영 서버는 `98a87d9d`(10/31 12:17 배포)에서 멈춰 있었다. 이후 배포 시도 6건이 모두 릴리스 단계 pytest에서 실패했다(muse API 테스트 2회, 게임 e2e와 게임 서빙 보안 테스트의 Docker 마운트 오류 4회).
- 로컬 `back` 체크아웃은 원격보다 530커밋 뒤처져 있고 다른 세션의 미커밋 변경이 61개다. 이 체크아웃의 코드를 읽으면 낡은 정보를 얻는다.
- Docker 마운트 경합에 대한 재시도가 `games/isolation.py`에 이미 들어 있다(실제 효과는 배포 게이트에서 확인 필요). 같은 테스트는 로컬에서 통과했다. 내 푸시(69dc15b9) 뒤 배포 예약 `b7ec4adc`를 넣었다. 게이트 통과 여부는 `deploy/deploy.sh status b7ec4adc`로 확인한다.
- 10/31 14:49에 `QueuePool limit of size 5 overflow 3 reached`로 작업자 Run 3건이 실패했다. `database_pool_size` 기본값이 5다(`config.py`). 이 파일은 다른 세션이 수정 중이어서 건드리지 않았다.

## 하지 않은 것과 이유

- `lead.md`의 모델 정책 수정: 사용자가 정한 정책이라 모순만 보고한다.
- 검증 대상 확대(Codex·Claude 결과도 독립 검증): 비용이 크게 늘어난다. 사용자 판단이 필요하다. 먼저 `상태:` 줄 도입 후 부분·막힘 비율을 2주 본 뒤 정하는 것을 권한다.
- `api/orchestrator.py`, `manager.py`, `config.py`: 다른 세션이 수정 중이라 건드리지 않았다. `상태:` 줄은 결과 첫 줄에 오므로 `list_workers`의 `last_result` 300자 안에 보인다. 전용 필드는 필요해지면 추가한다.
- 프론트와 front 저장소: 범위 밖.
