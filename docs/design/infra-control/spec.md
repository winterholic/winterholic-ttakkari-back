## 2. I3.1 첫 화면 우선순위와 상세 진입 흐름

### 2.1 사용자가 첫 화면에서 답을 얻어야 하는 5개 질문 (제안)

| # | 질문 | 첫 화면의 답 | 화면 위치 |
|---|---|---|---|
| 1 | 지금 전체가 괜찮은가 | 전체 상태 한 단어(정상/주의/문제/미확인), 관측 범위, 마지막 시각 | 맨 위 상태 카드 |
| 2 | 어디가 문제인가 | 조치가 필요한 서비스·호스트 목록 (심각도 순, 같은 심각도는 오래 지속된 순) | 상태 카드 바로 아래 |
| 3 | 얼마나 심각하고 언제부터인가 | 심각도 배지, 유지 시간("12분째"), 영향 한 줄 | 목록 행 |
| 4 | 무엇을 먼저 확인하나 | 근거 한 줄, 다음 확인 1~2개 | 목록 행(근거) + 상세(다음 확인) |
| 5 | 더 보려면 어디로 가나 | 상세 화면의 확인한 값·판정 기록, 그 아래 Grafana/Dozzle 링크 | 상세 |

### 2.2 동선

`전체 상태 → 조치 필요한 항목 → (영향·근거) → 상세(다음 확인·확인한 값·판정 기록) → 외부 Grafana/Dozzle`

- 정상일 때는 상태 카드, "조치가 필요한 항목: 없어요", 호스트 3줄, 접힌 수집원·서비스만 남긴다. 모바일에서 한 화면 반 안에 끝난다.
- 외부 도구 링크는 상세 맨 아래에 두고 "더 자세히 보려면 · 선택"이라 적는다. 첫 화면에는 두지 않는다. 방문이 일상 점검의 필수 단계가 아니기 때문이다.
- 모바일은 목록 → 상세를 **화면 전환**으로 연다(뒤로가기 버튼, Esc, 목록 행으로 포커스 복귀). 데스크톱은 **왼쪽 목록 + 오른쪽 고정 상세**이고 첫 항목이 기본 선택된다.

### 2.3 일부러 뺀 항목과 이유

| 뺀 것 | 이유 |
|---|---|
| 코어별 CPU, 프로세스 상위 목록, 네트워크 속도 | 기존 `/resources`가 이미 담당한다. 일상 점검의 5개 질문과 무관하다 |
| 컨테이너 개수·목록 | 개수를 확정할 근거가 없다(미확인). Docker 소켓은 브라우저에 넘기지 않는다(I2.2 원칙) |
| 전체 로그 스트림 | Dozzle의 몫이다. 첫 화면은 판정 근거만 보인다 |
| 장기 추세 차트 | Grafana의 몫이다. 상세에서 링크로만 연결한다 |
| 자동 복구·재시작 버튼 | 현재 범위 제외. 상세에 "조치는 사람이 판단해요, 자동 조치를 하지 않아요"를 명시한다 |
| AI 분석 진입점 | I6 범위. 시안에 두지 않았다 |
| 이벤트 타임라인의 추정 사건 | 원천이 없으면 만들지 않는다. "판정 기록"은 수집 판정 규칙의 결과만 적고 그 사실을 딱지로 밝힌다 |

## 3. 상태 어휘와 판정 규칙 (I2.3 확정 전 제안)

| 상태 | 뜻 | 표시 |
|---|---|---|
| 정상 | 관측 범위에서 확인했고 기준 안이다. **관측 범위와 마지막 시각을 함께** 적는다 | 초록, 체크 아이콘 |
| 주의 | 기준을 넘었거나 일부를 확인하지 못했다 | 노랑, 삼각형 |
| 문제 | 일정 시간 유지된 이상이 확인됐다. 단일 순간 값으로 확정하지 않는다 | 빨강, X 원 |
| 미확인 | 지금 상태를 알 수 없다(응답 없음, 권한 없음, 값이 오래됨) | 회색, 물음표 |

- 상태는 **색 + 아이콘 + 글자**로 나타낸다. 색만으로 구분하지 않는다.
- 신선도는 상태와 **별개 축**이다. 마지막 값이 기준보다 오래되면 항목 상태가 정상이어도 전체는 "미확인"이고, "마지막으로 확인된 상태: 정상"을 따로 적는다.
- 전체 상태 = 문제 > 주의 > (일부 확인 불가면 주의) > 정상. **확인하지 못한 범위는 정상으로 세지 않는다.** 이 규칙이 "정상" 오표시를 막는 핵심이다.
- HTTP 서비스 응답과 exporter up 은 구별한다. 시안의 Loki 상세는 "exporter up=1(수집은 됨)"과 "/ready 응답 없음"을 별도 행으로 보여 준다.
