# AI Research Lab v2 리팩토링 요구사항 (2026-10-25 사용자 지시서 요약)

원문: 2026-10-25 사용자 지시서 §0~15. 기획 세션 manage_work(original_request)에 원문 전체가 보존돼 있다. 이 문서는 구현자가 읽는 요구 정본이며 원문 항목을 누락 없이 옮겼다.

## 0. 성격
- 기존 Lab이 최초 요구보다 축소 구현됐다(연구 이력·근거 관리 중심). 원래 철학을 복원하는 **전면 리팩토링**이다. 기능 몇 개 추가나 화면 미화가 아니다.
- 조사→설계→WBS→구현→통합→검증→배포까지 이어서 한다. 감사 보고서로 끝내지 않는다.
- 일반적인 설계·구현 결정은 스스로 내린다. 단계별 승인을 묻지 않는다. 예외: 실제 데이터 삭제, 보안 설정 변경, 운영 서비스 위험 중단, 유료 리소스.

## 1. 제품 철학
AI/ML 시스템의 거의 모든 계층에서 개선 가능성을 탐색하고, 방법을 조합·실험·검증해 최적 결과물을 만드는 종합 연구실.
1 대상·목표 정의 2 개선 가능 계층 탐색 3 알려진 방법론·실험 방법 제시 4 적용 조건·효과·비용·부작용 확인 5 하나/여러 방법 선택 6 튜닝 파라미터·실험 환경 구성 7 실제 실행 또는 기존 실행기 호출 8 성능·품질·자원·비용·재현성 비교 9 성공·실패 원인 기록 10 최적 결과물·설정 보존 11 새 가설·방법 도출 12 이후 연구에서 재사용.
- 유명 기법만이 아니라 응용·조합·새 아이디어·미검증 가설까지 연구 가능해야 한다.
- 대상: LLM, SLM/온디바이스, Embedding, Reranker, RAG, TTS, STT, 이미지 생성, 영상 생성, Multimodal, 전통 ML, 분류·추천·검색, 서빙·추론 인프라, 데이터 파이프라인, GPU/CPU/메모리, 커널·컴파일러·실행 엔진, 에이전트·오케스트레이션. 목록 밖 분야도 코드·DB 대수정 없이 수용.
- **연구 대상, 개선 계층, 방법론, 실험 실행기는 서로 독립 개념.**

## 2. 방법론 체계
2.1 `kind=method` 노드 재검색은 유지 가치가 있으나 카탈로그를 대체하지 못한다. 구분: Method Definition / Category / Target Domain / Optimization Layer / Parameters / Compatibility / Execution Adapter / Evaluation Protocol / Evidence / Research History. 정적 방법 정의와 실험별 가설·관찰·결과 분리. 테이블을 무조건 늘리지 말고 가장 단순·일관된 설계.

2.2 다차원 분류(단일 트리 금지, 축 조합 검색):
- A 대상: LLM, TTS, STT, RAG, 임베딩, 생성 모델, 전통 ML, 시스템 인프라 등
- B 계층: 모델 구조, 학습, 데이터, 전처리, 후처리, 토큰화, 인코딩, 디코딩, Attention, KV Cache, GPU Kernel, 컴파일러, 런타임, 메모리, 하드웨어, 네트워크, 서빙, 스케줄러, 시스템 아키텍처
- C 목표: 정확도, 품질, 속도, 지연, 처리량, 메모리, GPU, CPU, 비용, 안정성, 재현성, 확장성, 일관성, 에너지
- D 개입: 파라미터 변경, 알고리즘 변경, 모델 교체, 파이프라인 재구성, 전후처리 추가, 커널 변경, 캐싱, 압축, 병렬화, 학습, 데이터 증강, 컴파일 최적화
- E 연구 방법: Baseline, A/B, Ablation, Parameter Sweep, Grid, Random, Bayesian, 반복 측정, 민감도, 프로파일링, 오류 분석, 조합 실험
- F 실행 가능 상태: 즉시 실행 가능 / 기존 도구 연동으로 실행 가능 / 일부 기능만 지원 / 실행 어댑터 구현 필요 / 연구 가설 단계 / 현재 환경 실행 불가. **등록됐다고 실행 가능으로 표시 금지.**

2.3 초기 카탈로그(빈 카탈로그 금지). 최소 포함:
- LLM/추론: Quantization, Pruning, Distillation, KV Cache Quantization, KV Cache Reuse, Flash Attention, Speculative Decoding, Continuous Batching, Prefix Caching, Kernel Fusion, Memory Layout Optimization, Prefill/Decode 분리, CPU/GPU Offloading, Runtime/Backend 비교, Prompt Length·Context 최적화
- 학습: LoRA, QLoRA, Fine-tuning, DPO, LR Schedule, Optimizer 비교, Gradient Accumulation, Mixed Precision, 데이터 샘플링·증강, 하이퍼파라미터 탐색
- RAG: Chunking, Hybrid Retrieval, Query Expansion, Query Rewriting, Reranking, Embedding Model 비교, Index 구조, Context Compression, Retrieval Cache, 결과 결합(Fusion)
- TTS: Text Normalization, G2P, Pronunciation Dictionary, Phoneme Alignment, Prosody Control, Duration Prediction, Vocoder 비교, Audio Postprocessing, Sentence Segmentation, Speech Stitching, Streaming Synthesis, Sampling/Decoding 설정, Voice Consistency 평가
- STT: VAD, Chunk Window, Overlap, Beam Search, Temperature Fallback, Context Conditioning, Hallucination Detection, Diarization, Language Detection, Audio Preprocessing
- 시스템: 메모리 대역폭, 병렬 처리, 배치 크기, CPU Thread, GPU Kernel Profiling, Metal/CUDA 경로 비교, 연산·데이터 이동 최소화, 메모리 할당, 컴파일·런타임 최적화, 워크로드별 엔진 선택
출발점일 뿐. 숫자 채우기 금지. 각 항목의 기술적 의미·적용 범위·실행 방법·근거 또는 미검증 상태 명시. 모델·하드웨어별 지원이 다른 기법을 공통 지원처럼 취급 금지.

2.4 새 아이디어(예: "가중치 대신 GPU 커널 메모리 접근 패턴 변경으로 출력 속도 개선?"): 등록→대상·계층 지정→가설→지표 선택→실행 가능성 분석→실험 설계→실행기 연결 또는 외부 결과 등록→검증→카탈로그 편입. 사용자가 플러그인을 개발해야 하면 실패. 지원 안 되면 무엇이 가능하고 어떤 어댑터가 필요한지 보여준다.

## 3. 실험 엔진
3.1 구분: Research Project / Method / Experiment Definition / Configuration / Run / Measurements / Analysis / Artifact / Decision. 같은 설정 5회 실행 ≠ 정의 5개. 필요하면 Definition과 Run 분리.
3.2 복수 방법 선택·조합(예: Q8 KV+Flash Attention, Hybrid+Rerank, Normalization+G2P+사전, Speculative+Batching). 충돌·선후·적용 조건·검증 필요성 표현. 조합 효과는 별도 실험으로 검증.
3.3 JSON 직접 입력을 기본으로 쓰지 않는다. 레지스트리 파라미터 정의로 폼 자동 구성: 숫자, 범위, 열거, Boolean, 다중 선택, 모델 선택, 데이터셋 선택, 파일 선택, 실행 환경 선택, 고급 설정. JSON은 전문가 옵션.
3.4 공통 구조로 표현: 단일, Baseline 비교, A/B, 반복, Grid, Random, Bayesian, Ablation, 다중 변수, 조합, 조건부 탐색. 직접 다 구현 금지(Optuna 등 온디맨드 재사용 가능). 지원/미지원 명확 구분. 조합 폭발 방지 예산·제한.

## 4. 기존 실행기 통합
4.1 새 AI 실행 생태계 중복 구축 금지. 존재: 로컬 LLM, Qwen 실험 도구, 호스트 GPU 계측, Whisper STT, Kokoro TTS, 임베딩·RAG, 오케스트레이터, Claude Code/Codex 하네스, 테스트 실행 환경, 파일·아티팩트 관리. 실제 동작·API·경로를 조사하고 연결 우선. 기존 큐·프로세스 관리·자원 보호·로그·산출물 저장 재사용. 별도 거대 스케줄러는 최후 수단.
4.2 Adapter 계약 최소: 실행기 ID·버전, 지원 영역, 지원 방법·파라미터, 필요 입력, 환경·의존성 확인, 예상 자원, 시작, 상태 조회, 취소·정리, 원본 출력, 측정 변환, 결과물 등록. 허위 기능 노출 금지. 기존 안정 도메인을 무리하게 바꾸지 않는다.
4.3 수직 통합 우선:
- A LLM 추론: 기존 로컬 모델·GPU 계측. TTFT, tok/s, 총 시간, 메모리 피크, KV 설정, Context, CPU/GPU 이용, 출력 품질, 오류율
- B RAG/임베딩: 기존 검색 평가 확장·RAG 도구 연결. Recall@k, MRR, nDCG, 검색 지연, 인덱스 크기, 임베딩 처리량, 리랭킹 효과, (평가 가능 시) 답변 품질
- C TTS: Kokoro 등 실제 파이프라인 설정·전후처리 비교. 한국어 발음 오류, 숫자·기호·외래어, 사전 전후, 생성 속도, RTF, 음성 길이, 문장 누락, 자연스러움. **STT 재인식 오류율과 실제 청취 품질 구분.**
환경상 불가 기능은 실행 가능한 동등 사례로 대체하고 이유 기록.

## 5. 프론트엔드
기존 목록→상세→지식→실험→타임라인 구조를 재설계. 열자마자 "무엇을 연구하고, 어떤 방법으로 실험할 수 있으며, 어떤 결과가 나왔는지" 이해.
① 대시보드: 진행 연구, 최근 실험, 주요 성능 변화, 성공·실패 요약, 실행 상태, 최적 결과물, 검증 필요 결과, 다음 연구 후보
② 방법론 라이브러리(가장 중요): 분야·계층·목표별 탐색, 적용 환경, 실행 지원 상태, 상세 설명, 파라미터, 기대 효과·부작용, 기존 연구 사례, 논문·근거, 실험 설계로 이동. 수백 개에서도 검색·필터·태그·관련 기법·조건부 연결
③ 실험 설계실: 목표→Baseline→대상→방법→조합→튜닝→지표→실행 환경 확인→생성. 기본값·설명. 불가능 조합·자원 초과는 실행 전 경고
④ 실험 모니터: 실행 중 실험, 진행 상태, 자원, 실시간 측정(지원 시), 로그, 실패 원인, 중단·재개 가능 여부, 산출물. **진행률 지어내기 금지**
⑤ 결과 비교·분석(핵심): Baseline 대비 개선·퇴보, 실험별 차트, 다중 지표, 시간 추이, 반복 분포, 메모리·속도 trade-off, Pareto, 실패 유형, 방법·설정 차이, 재현성·비교 가능성. JSON 덤프를 기본 UI로 쓰지 않는다
⑥ 연구 기록·결과물: 목표, 시도 방법, 가설, 결과, 성공·실패 근거, 논문, 결론, 최고 설정, 모델·체크포인트·파일, 재현 환경, 후속 후보. 노드·근거·불변 타임라인 보존하되 DB 레코드 목록처럼 보이지 않게.
UX 10문: 시도 가능한 방법? 현재 실행 가능한 방법? 이전 시도? 적용 설정? 조합? 개선/악화 폭? 성공 이유·실패 원인? 재실행 가능한 실험? 현재 최고 결과물? 이전 연구 재사용 방법? 디자인 시스템 재사용, 기존 화면 구조 고집 금지.

## 6. 성과·결과물
모든 원본 측정·실패 보존. 최적 결과물은 별도 관점(최고 품질, 최속, 메모리 효율, 균형 추천, 데이터셋별 최고, 채택 파이프라인, 검증 필요 후보). **최적은 목표·지표·제약에 종속.** 단일 점수로 전면 최적 표시 금지.
아티팩트: 모델 파일/경로, LoRA, 설정, 체크포인트, 평가 데이터, 로그, 측정, 그래프, 음성·이미지 샘플, 보고서. 기존 파일 보관함 재사용, 복제 불필요 시 참조만. 출처·연관·재현성 보존.

## 7. 지식 순환(기존 강점 유지)
근거·논문 주장·실측·가설·해석 구분. 실패 삭제·매몰 금지. 과거 실패를 다른 환경에서 자동 제외 금지. 결과→카탈로그·다음 설계로 환류(예: KV 설정이 메모리만 절약→KV×Attention 상호작용 가설 등록→후속 검증→입증 시 방법·조건 기록). 논문 결과와 따까리 재현 결과 혼동 금지.

## 8. 아키텍처 원칙
기존 연구 기록 구조 재사용 / 프론트·백·실행기 책임 분리 / 방법 정의와 실행 코드 분리 / 분야별 실행기 플러그인 / 기존 MCP·하네스·인프라 재사용 / 신규 데몬·DB·MQ·상시 서버 금지 / 원본과 해석 구분 / 미측정 성능을 추정으로 표시 금지 / 과도한 대체 실행 환경 금지 / 특수 요구로 전체 복잡화 금지. 필요 시 지연 로딩. 배포 병목·3슬롯 고려: Lab 변경이 오케스트레이터·타 플랫폼 배포를 막지 않게. 배포 아키텍처 전체 개편은 범위 밖.

## 9~11. 실행 전략
- 반복 감사·설계 토론·ADR 남발·작은 게이트·과도한 분할·검증된 모듈 재검증·테스트 인프라 과잉 금지. 합리적 가정을 명시하고 진행(데이터 손실·보안·잘못된 측정·운영 장애는 예외).
- 선행 설계 한 번에: 유지/교체, 레지스트리, 어댑터 계약, 실험·실행·측정 모델, 프론트 IA, 마이그레이션, 실행기 재사용, 완료 기준. 중대 결함 없이 뒤집지 않는다.
- Phase 1 기반 설계 → 2 카탈로그(레지스트리·초기 카탈로그·검색 필터 API·적용 조건·실행 상태·화면·신규 등록) → 3 실험 설계·실행(선택·조합·폼·Definition/Run·어댑터·도구 연동·Baseline·반복·외부 결과) → 4 분석·성과(다지표·조건 차이·차트·실패·결과물·최적 설정·재활용) → 5 통합·검증·배포. Phase별 승인 대기 금지.
- 테스트 필수: 마이그레이션·기존 데이터 보존, 레지스트리 CRUD·검색, 선택·조합, 설정 유효성, 어댑터 계약, 결과·실패 저장, 측정값·출처 무결성, 프론트 핵심 흐름, 연동. 대표 통합: 연구 생성→방법 선택→설정→실행→시각화→최적 결과물→재진입. 최소화: 항목별 반복 테스트, CRUD E2E 중복, 무변경 영역 전체 재실행, 의미 없는 mock, 스냅샷 과잉.
- 검증 순서: 정적·타입 → 수정 영역 단위 → API 계약 → 대표 수직 통합 → UI 상호작용 → 최종 회귀·빌드 → 배포 후 스모크.
- 테스트 통과 ≠ 연구 성과. 실행 성공 / 측정 신뢰성 / 조건 동일성 / 반복 변동성 / 실제 개선 / 부작용 구분.
- 문제 분류: A 필수→직접 해결, B 우회 가능→대안+후속 기록, C 무관 부채→분리 기록, D 승인 필요→보류하고 다른 작업 계속.

## 12. 인수 시나리오(데이터 저장·복원·화면 이해까지)
- A LLM 추론: 속도 연구 생성→라이브러리에서 KV/디코딩/커널/메모리/런타임 계층 탐색→실행 가능한 방법 선택→기준 vs 변경 비교→속도·지연·메모리·품질 확인→최적 후보 설정·결과물 저장. 실행 불가 커널 최적화도 설명·지원 상태 확인 가능.
- B TTS 발음: 한국어 발음 개선 연구→Normalization·G2P·사전 등 탐색→지원 방법·설정 선택→대표 입력으로 비교→발음 오류·생성 속도 확인→음성 파일·채택 설정을 결과물로 보존.
- C RAG: 검색 정확도 연구→Chunking·Hybrid·Rerank 탐색→지원 실험 구성→Recall@k·MRR 비교→무개선·퇴보도 보존→다음 연구에서 재참조.
- D 새 방법: 카탈로그에 없는 아이디어 등록→목표·계층·가설·지표 작성→기존 어댑터 확인→없으면 미지원 명확 표시→실행기 연결 또는 외부 결과 등록으로 진행→검증 후 결과와 함께 재사용 가능한 카탈로그 항목으로 관리.

## 13. 완료 기준
Registry 존재 / 초기 카탈로그 실데이터 / 새 방법·가설 자유 추가 / 실행 지원 정확 표시 / 선택·조합 설계 / 친화적 설정 UI / 기존 실행 도구 실제 연결 / 대표 분야 실제 실행 경로 확인 / 반복 측정·저장 / 성과·실패·설정 차이 시각화 / 연구별 최적 결과물·설정 관리 / 과거 연구·방법 재사용 / 대표 시나리오 통과 / 기존 데이터·타 플랫폼 무훼손 / 프론트 빌드·백엔드 통합·회귀 통과 / 기존 배포 체계에서 사용 가능.
부분 구현을 완료로 보고 금지. 반대로 모든 기법의 네이티브 실행기를 완료 조건으로 삼지 않는다. **범용 구조가 동작하고, 대표 영역에서 실행·비교·성과 관리가 검증되고, 확장 가능한 상태**가 현실적 완료.
