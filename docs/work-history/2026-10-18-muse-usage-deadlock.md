# Muse 사용량 "낡은 값/조회 불가" 교착의 근본 수정 — 2026-10-18

## 원인 (실측과 추정을 구분)

**실측**
- 관측 이력(`account_usage_samples`, 읽기 전용): Muse 계정은 06:53 KST(5h 100%, reset 06:58) 이후 17:27:38까지 표본이 없다. 같은 시간대에 Antigravity 3계정은 매시간 5~28건씩 계속 측정됐다.
- 같은 구간의 Run 수: codex 232, claude 93, antigravity 25, **muse 1**(17:26:46, 사용자 명시 호출). 03:29 이후 17:26까지 Muse Run이 없다.
- 17:26:50 첫 호출 직후 스트림 관측이 5h 0%, reset 22:26:50(첫 호출 + 5시간)을 남겼다. 오늘 19:17 호스트에서 실제 수집기를 한 번 돌리면 5h 9%(reset 22:26)·주간 36%, login ok, `muse_quota_current=true`가 나왔다. 창이 첫 사용 시점에 시작되고, 쓰는 동안은 /usage가 값을 준다는 것과 일치한다.
- 코드 경로(교착의 직접 원인): `worker_routing.first_stage`는 확정 잔여량이 있는 후보(`measured`)가 하나라도 있으면 확정되지 않은 후보를 `usable`에서 아예 뺀다. `profiles.choose`도 확정 잔여량이 없는 후보를 맨 뒤로 민다. Antigravity·Claude·Codex는 항상 측정되므로 확정되지 않은 Muse는 어떤 `general`/`routine` 작업에서도 뽑히지 않는다. 뽑히지 않으니 스트림 관측이 생기지 않고, 관측이 없으니 계속 확정되지 않는다.
- 낡은 값을 현재 잔여량처럼 쓰지 않는 불변 조건(b427e31)은 이 교착을 만든 쪽이 아니다. 불변 조건은 옳고, 빠진 것은 "알 수 없는 상태에서 빠져나올 경로"였다.
- 추가로 발견: 수집기는 실패가 쌓이면 주기를 최대 30분까지 늘리는데(백오프), 스트림 관측이 새로 생겨도 백오프를 끊지 않는다. 17:27 관측 이후 다음 수집 표본이 17:52였던 것(25분 지연)과 맞는다. 이 지연이 백오프 때문이라는 것은 추정이다(수집기 내부 로그는 보호 구역이라 못 읽었다).

**추정(미확인)**
- 공급자가 유휴 창의 `/usage`를 생략한다는 점은 외부 보고(CodexBar 이슈)와 네이티브 CLI의 `Currently unavailable` 출력으로만 뒷받침된다. 공급자 응답 본문은 확인하지 못했다. 이번 설계는 이 가설이 틀려도(어떤 이유로든 알 수 없는 상태가 길어져도) 교착이 없도록 원인에 의존하지 않게 했다.

## 설계 결정

선택: **알 수 없는 Muse에 한해 비율 제한된 탐색 배정 + 새 관측 시 수집 백오프 해제**.

1. `profiles.muse_probe_eligible`: 확정 잔여량이 없는 Muse(관측 없음, 낡음, 초기화 뒤 미관측, 갱신 실패)가 30분(`MUSE_PROBE_INTERVAL`)마다 한 번 실제 작업을 받을 수 있게 한다. 알려진 한도 소진(`usage_limit_until`), 쿨다운, 로그인 없음, 직전 탐색 뒤 간격 미경과는 제외한다. 확정 잔여량이 있으면 탐색이 아니라 평소 headroom 순위로 간다.
2. `worker_routing.first_stage`는 탐색 후보를 `usable`에 포함하고, `profiles.choose`는 `balance_usage`일 때 탐색 후보를 먼저 뽑으며 그때 시각을 기록한다(await 없이 선택과 기록이 한 번에 일어나므로 동시 Run이 같은 탐색을 중복으로 가져가지 않는다).
3. `usage_collector`: Muse에서 실패 백오프 중에 스트림이 더 새로운 관측을 남기면(`cached.updated_at > last_fetch`, `MIN_REFETCH` 경과) 바로 한 번 다시 조회한다.
4. API: 초기화된 5시간 창은 기존대로 `unavailable`(퍼센트 0은 자리표시자)이고, 오류 문구에 "5시간 창이 초기화된 뒤 쓰지 않아 값이 없어요. Muse 를 쓰면 갱신돼요"를 덧붙인다. `account_usage`의 `model_capacity`에 `exploration_eligible`과 안내문을 더했다. 프론트는 바꾸지 않았다(작업 중인 다른 세션의 변경과 겹치지 않게, 기존 state 문구로 충분).

이유와 버린 대안
- "초기화 뒤 unavailable이면 0%·미사용으로 간주": 공급자 값 없이 수치를 만들어 내는 것이라 기존 불변 조건과 충돌한다. 쓰지 않았다.
- 주기적 재조회만 늘리기: 유휴 창을 공급자가 주지 않으면 몇 번을 조회해도 같다. 조회를 위한 모델 호출은 이 프로젝트가 금지해 둔 방식이다(2026-10-18-muse-usage-unavailable).
- 탐색은 실제 사용자 작업을 맡기는 방식이다. Muse 결과는 이미 독립 검증 대상(`needs_independent_verification`)이므로 안전망이 있다. 탐색은 계정·프로세스당 30분에 한 번이라 검증 부담이 늘어도 상한이 있다. 세 세대(generation)가 동시에 돌면 프로세스별 기록이라 최대 세 번까지 탐색할 수 있다(상한은 유지).
- 탐색 Run이 429로 실패하면 기존 쿨다운이 걸려 탐색 후보에서 빠진다.
- 이 경우 한 번 배정된 Muse 작업이 실패하면 기존 폴백 흐름(다른 후보로 재배정)을 그대로 따른다.

## 기본 모델 확인 (muse-spark-1.3)

- `config.worker_default_models["muse"]`와 `engine_models["muse"]`는 `muse-spark-1.3`만 가진다. `primary_target("muse")`와 모델 미지정 `engine="muse"` 작업자 배정은 1.3이다. 1.2나 알 수 없는 id를 명시해도 `engine_models`에 없으면 1.3으로 돌아간다(1.2 명시 지원은 코드에 없다. 요청은 "1.2는 명시 지정 시에만"이었으나 현재 코드에는 1.2 항목 자체가 없고 `muse-wonder-*`는 접근 실패 이력만 있다).
- `engine="auto"` 모델 미지정은 첫 단계의 첫 항목(Sonnet)이며 Muse가 기본이 되지 않는다. 고친 것은 없다. 테스트로 고정했다.
