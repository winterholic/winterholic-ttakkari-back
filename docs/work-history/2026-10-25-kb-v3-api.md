## MCP·에이전트 호환

- `kb_search(query, limit, mode)`, `kb_documents(query, limit, offset)`, `kb_document(document_id)`, `kb_evidence(passage_id, start, end)` 시그니처 불변(테스트가 파라미터 이름 목록을 고정).
- 기존 응답 필드 전부 보존. 추가: 어휘 검색·문서 상세의 `section_path, page_no, slide_no, time_start_ms, time_end_ms, chunk_kind, token_estimate`;
  하이브리드 검색 항목의 `match_paths, conflict_warning, canonical_facts`, 주장 항목의 `id, subject, text`, 응답의 `include_candidates`.
- 에이전트 API 에 후보 관계 옵션 `include_candidates`(기본 꺼짐)만 추가했다. MCP 도구에는 인자를 늘리지 않았다.
- 접근 반례(테스트): 개인 세션·개인 MCP 에서 work_only 문서·엔터티·근거가 안 보인다. 회사 세션·회사 MCP 는 기존대로 회사 문서만 보고 개인 문서는 새로 열리지 않는다.

## 백필 (KB3-103)

- `ttakkari.cli kb-backfill`(기본 dry-run, `--apply` 필요, 운영 환경에서는 `--confirm-production` 추가 필요), `kb_backfill.py`.
- 분류(문서마다 결정적): `skip_done / enqueue_only / rechunk_html_reparse / rechunk_same_body / skip_hidden / skip_unclassified / error`.
  새 청커의 계획(경계·절 경로·종류)과 현재 패시지가 같으면 재청킹하지 않는다 → 두 번째 실행은 아무 행도 만들지 않는다.
- 새 구조가 필요하면 같은 문서에 새 리비전(`supersedes_id`)을 쌓고 관측으로 현재로 만든다. 레거시 수집기 HTML(`trafilatura …+parse-1`)은 원본 바이트가 온전하면
  현재 수집기 파서로 다시 추출해 헤딩 구조를 되살린다. 원본이 없거나 손상됐으면 본문 그대로 구조 청킹하고 사유를 남긴다(헤딩은 복구되지 않는다).
  패시지 경계가 우연히 계획과 같아도 레거시 HTML 은 새 리비전이 필요하다(아니면 parsing 이 `collector_html_structure_revision_required` 로 영구 held).
- 숨김(hidden) 문서와 접근 행이 없는 레거시 문서는 건너뛰고 보고한다(`--include-hidden`, `--classify-legacy` 로 명시적으로만 처리).
  `--classify-legacy` 는 그 문서의 현재 노출(personal 범위, global)을 접근 행으로 명시할 뿐 노출을 넓히지 않는다.
- 재개·중단: 상태는 DB 에서 다시 계산하므로 같은 명령 재실행이 곧 재개다. 묶음(`--batch-size`)마다 commit, 문서마다 savepoint(실패 격리), SIGINT/SIGTERM 은 현재 문서를 끝내고 멈춘다.
  `progress.jsonl`(문서별)·`state.json`(커서·집계)이 보고서 디렉터리에 남는다. 동시에 둘이 돌지 않게 advisory lock 을 쓴다.
- 롤백(`--rollback RUN_ID|all`): 이전 리비전을 가리키는 새 관측을 덧붙여 현재로 되돌리고, 되돌린 리비전의 active 주장을 superseded 로, 이전 리비전의 superseded 주장을 active 로 맞추고 정본을 다시 만든다. 원장 행은 지우지 않는다.
  백필 뒤 재수집(새 관측)이 생긴 문서는 되돌리지 않는다. `enqueue_only`(추가 전용 패시지·작업)는 되돌릴 대상이 아니다.

### 파이프라인 잡 백필 (배포 겹침 구간 및 0071 기존 문서 보충)

- 구 세대(0071) 코드는 `enqueue_pipeline_job`을 호출하지 않아, 0071 기존 문서 및 배포 겹침 구간에 등록된 문서는 `kb_pipeline_jobs`가 없다.
- `ttakkari kb-enqueue-jobs` (또는 `ttakkari kb-backfill --enqueue-jobs-only`, `run_enqueue_jobs_backfill`):
  - 리비전 본문이나 패시지를 변경하지 않고, 잡이 없는 현재 리비전만을 찾아 `enqueue_pipeline_job`을 생성하는 멱등 백필 (`knowledge-backfill` 원문 버전 보존과는 별개).
  - 배치 처리(`--batch-size`, 기본 10), dry-run 기본(`--apply` 시만 실제 커밋, 운영 환경은 `--confirm-production` 필요).
  - 재실행 안전: 이미 잡이 존재하는 리비전은 `skip_has_job`으로 건너뛰므로 2회차 실행 시 `enqueued=0`.
  - 가시성 보존: `KbDocumentAccess`를 수정하지 않으며, 숨김 문서는 기본 스킵(`--include-hidden` 시 포함). 파이프라인 워커 실행 시 `work_only` 가시성이 엔터티/주장에 그대로 유지됨.
  - L2 예산 준수: 파이프라인 워커가 L2 일일 예산 원장을 준수하여 예산 소진 시 `degraded`로 안전하게 완료.
- 리허설 (corpus 9건: 기존 job 1, hidden 1, 대상 7건):
  - dry-run: `examined=9, enqueued=7, skipped_has_job=1, skipped_hidden=1, apply=False`, DB 변화 0건.
  - apply: `enqueued=7, skipped_has_job=1, skipped_hidden=1`, DB `KbPipelineJob` 1 -> 8건.
  - 2회차 apply: `enqueued=0, skipped_has_job=8, skipped_hidden=1`, 멱등성 검증 완료.
  - 워커 소진: work_only 문서에서 추출된 엔터티/주장의 `visibility="work_only"` 보존 확인.

## 알려진 한계·미검증

- 운영 규모(문서 수만, 문서 28k자)에서의 0072 잠금 시간, 백필 시간, 임베딩 시간은 측정하지 못했다. 운영 36건의 실제 본문으로 리허설하지 않았다(운영 DB 접근 금지).
- 실제 외부 URL fetch 는 네트워크에서 실행하지 않았다(SSRF 방어 fetcher 는 기존 모듈이고 시험은 가짜 fetch 와 사설 주소 거절만 본다). URL 은 수집기 권리 정책 경로가 아니라 사용자 지정 단일 페이지 저장이며 robots.txt 를 확인하지 않는다.
- OCR·STT·구형 Office 는 지원하지 않고 held 로 남는다(파서 계약대로). 스캔 PDF·mp3·.doc·알 수 없는 바이너리를 held 로 만드는 것까지만 검증했다.
- 충돌 탐지는 같은 개념을 설명하는 문서끼리 정의 표현이 다르면 `value_contradiction` 을 많이 만든다(리허설 36건에서 49건). 이 묶음은 탐지 규칙을 건드리지 않았다. 운영 코퍼스에서 충돌 목록이 넘칠 위험이 있다.
- 접근 행이 없는 레거시 문서의 처리 방침(`--classify-legacy`)과 숨김 문서 처리는 사람이 정해야 한다. 운영에 이런 문서가 몇 건인지는 확인하지 못했다.
- 웹 세션 기본 범위를 global 만(개인 세션 기준)으로 했으므로 회사(work_only) 문서는 통합 목록·검색·그래프에 안 나온다. 설계 KD-01 은 owner 웹에서 work_only 도 보인다고 적었다. 리드 결정(웹은 personal 세션 기준)을 따랐고, 바꾸려면 `kb_access.create_web_context` 한 곳이다.
