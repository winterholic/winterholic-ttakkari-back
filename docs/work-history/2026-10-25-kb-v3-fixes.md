### 1. 접근 행이 없는 문서가 personal 에 노출된다 (보안)

- 원인: `kb_access.document_access_filter`/`passage_access_filter`가 "접근 행이 아예 없으면 global 허용 컨텍스트에 노출"하는 레거시 분기를 갖고 있었다. `kb_library.scope_filter('personal')`도 같았다.
  접근 행을 안 쓰는 수집 경로는 CLI `kb-ingest`와 research `import_source` 두 곳이었다.
- 수정:
  - `kb_access.unclassified_documents_visible(ctx)` 단일 규칙: 접근 행이 없으면 work_only 취급. work_only 를 허용하고 origin_scope 필터가 없거나 work 인 컨텍스트에서만 보인다. 문서·패시지 필터가 이 규칙을 쓴다. `kb_library.scope_filter`도 같은 규칙이다(personal 에서는 안 보이고 work 에서만 보인다).
  - `kb_library.ensure_document_access(db, document_id, scope=...)`를 단일 쓰기 경로로 만들고 `register_text`, research `import_source`(연구 scope 사용, 불일치는 409), CLI가 모두 쓴다.
  - CLI `kb-ingest`에 `--scope {personal,work}`를 추가했고 기본은 `work`(work_only)다. 지정하지 않은 scope 는 미상이므로 fail-closed 다.
  - API 모듈 docstring의 "레거시 미분류는 personal 전용" 문장을 현재 규칙으로 고쳤다.
- 기존 시험 3건이 옛 동작(접근 행 없는 문서가 personal 에 보임)을 기대하고 있어 의도는 유지한 채 수정했다: `test_kb_observations`(접근 행 추가), `test_kb_library_api`의 백필 시험(work scope 로 검색, personal 은 계속 0건), CLI 시험(`--scope personal` 명시).
- 운영 기존 데이터: **백필 CLI 방식**을 택했다. `ttakkari kb-backfill-access`(`src/ttakkari/kb_access_backfill.py`).
  - 마이그레이션이 아닌 이유: (a) 미상 문서의 scope 분류에 사람의 검토가 필요하다. (b) 새 마이그레이션은 `deploy/generation-contract.json` 갱신이 필요한데 그 갱신은 범위 밖이다(`tests/test_generation_deployment.py`가 head 조상 체인을 요구한다). (c) 온라인 마이그레이션은 statement timeout 30초 안에 끝나야 하지만 백필은 500건 배치 커밋이다.
  - 기본은 dry-run이다(쓰기 0, 분류 개수와 샘플만 출력). `--apply`는 `--confirm-database <접속 DB 이름>`을 함께 줘야 하고 아니면 종료 코드 2로 거부한다. `ON CONFLICT DO NOTHING`이라 멱등이다.
  - 분류: research doc_key(`research:work:`/`research:personal:`), Collector 원본 origin_meta, 운영자가 `--personal-doc-key-prefix`로 지목한 접두사만 근거가 있어 personal 이 될 수 있다. 나머지 미상은 work_only 다.
  - 백필 전에도 조회 규칙이 접근 행 없는 문서를 work_only 로 취급하므로 이 백필은 노출을 넓히지 않는다. 얻는 것은 파이프라인이 접근 행 없는 문서의 엔터티를 버리지 않게 되는 점이다.

### 2. L1 시드 매칭이 대문자 영어 이름을 버린다

- 원인: `tokenize()`가 토큰을 casefold 하는데 `match_known_entities`가 `body.find('kubernetes')`로 원문에서 위치를 찾았다. 원문 `Kubernetes`는 못 찾아 span -1, 인용 ""가 되어 quote verifier가 근거 없는 언급으로 버렸다.
  그래서 정의문 없이 `Kubernetes`가 일반 문장에 나오는 영어 문서는 엔터티가 만들어지지 않고 `쿠버네티스`/`k8s`가 이어지지 않았다.
- 수정: `extract_l1._fold_with_origin`/`_locate_original_span`. 본문을 토큰과 같은 형태(NFKC+casefold)로 접고 글자별 원문 인덱스를 보관해, 접힌 토큰의 위치를 원문 좌표로 되돌린다. 인용은 항상 `body[start:end]` 원문 그대로다.
  단어 중간의 부분 문자열(예: `Googlekubernetesx`)은 언급이 아니다. 한글 뒤 조사는 허용한다.
- 불변식 유지: 언급은 원문 span 이 성립해야만 만들어지고(`근거 없는 언급 금지`), 시드 별칭만 출현 근거를 면제받으며 `extracted` 별칭은 인가된 패시지 본문 출현을 요구한다(`entity_alias_access_filter` 그대로). 시험이 이를 고정한다.

### 3. 검색 필터와 표시

- `domain`: 수집 경로가 `source_meta.domain`을 쓰지 않아 항상 비었다. `kb_store.ingest_source`가 URL 출처(`locator`가 http/https)의 호스트를 `source_meta.domain`에 기록한다.
  `kb_sources`는 UPDATE 를 거부하는 불변 원장이라 기존 행은 갱신하지 않고, 필터(`source_domain_expression`)와 표시(`source_domain`)가 기록값이 없으면 `locator`에서 같은 규칙으로 도출한다. 이것이 기존 행 백필이다. 응답의 `document.domain`도 `KbDocument.domain`(없는 속성)이 아니라 이 값을 쓴다.
- `status=historical`: 원인은 SQL 3치 논리다. 관측이 없으면 `KbRevision.id = NULL`이 NULL 이라 `not_(current)`도 NULL 이 되어 비현재 리비전이 전부 탈락했다. `_current_revision_filter`가 관측 유무를 명시해 항상 참/거짓이 되게 했다. 현재성의 의미는 바꾸지 않았다.
- `has_conflict`: 같은 엔터티를 언급하기만 하는 패시지에도 붙었다. 이제 열린 충돌의 당사자 주장(a 또는 b)을 `supports`로 뒷받침하는 근거 패시지에만 붙는다. 접근 필터는 그대로다.
  `test_kb_v3_integration_flow`의 해당 시험이 제목만 있는 비당사자 패시지까지 has_conflict 이길 요구했다(결함을 기대값으로 고정). 정의 문장 패시지만 True 로 바꿨다.

### 4. 현재성

- 원인: 온톨로지 쪽 현재 리비전이 곳곳에서 관측 `event_time` 최신을 먼저 봤다(canonicals, conflicts, graph_query). 반면 대체(superseded) 전환은 rev_no 기준이다. rev_no 가 큰 리비전의 event_time 이 더 과거면 낡은 리비전 주장은 superseded 가 되고 현재 리비전 주장은 "현재가 아님"으로 걸러져 정본이 비었다.
- 수정: `kb_ontology/currency.py`가 문서 안 현재 리비전을 rev_no 최대로 정하는 단일 정의다. canonicals, conflicts, graph_query가 모두 이를 쓴다. 문서 간 시간 비교(`freshness_ts`, 최신성 가산)는 건드리지 않아 event_time 을 유지한다.
- 정정 개정 뒤 충돌이 open 으로 남는 문제: 두 원인이 있었다. (a) `update_superseded_assertions`가 `active`만 대체해서 충돌 당사자라 `disputed`인 구버전 주장은 영원히 남았다. (b) 충돌을 닫는 곳이 없었다. 이제 `active/disputed` 모두 대체하고 당사자가 대체된 열린 충돌을 닫는다.
  - `kb_conflicts.status`의 CHECK 에 `stale`이 없다. 값을 추가하려면 새 마이그레이션과 generation contract 갱신이 필요한데 범위 밖이라 기존 값을 쓴다: 살아남은 당사자가 있으면 그쪽 `resolved_a`/`resolved_b`, 둘 다 대체되면 `resolved_both_valid`. `resolved_by='system:revision_supersession'`, `resolution_note`에 사유를 남긴다. 둘 다 대체된 경우의 `resolved_both_valid`는 의미가 거칠다(미검증 의미 부담, 아래 남은 결정 참고).
  - 살아남은 당사자가 다른 열린 충돌에 걸려 있지 않으면 `disputed`에서 `active`로 되돌린다.
  - canonicalizing 처리기와 `update_canonicals_for_revision`이 `supersedes_id`뿐 아니라 더 낮은 rev_no 의 주장 주어 엔터티까지 갱신 대상에 넣어 `has_open_conflict`가 다시 계산된다.

## 남은 결정과 미검증

- **A→B→A 복귀와 늦게 도착한 오래된 스냅샷**: 검색의 패시지 현재성(`kb_library._current_revision_filter`, `tests/test_kb_observations.py`)은 의도적으로 관측 ledger(event_time)를 따르고 이번에 바꾸지 않았다.
  온톨로지의 문서 안 현재 리비전은 rev_no 라서, 늦게 도착한 오래된 스냅샷이 있는 문서는 검색의 "현재 패시지"와 정본·충돌의 "현재 리비전"이 서로 다른 리비전을 가리킬 수 있다. 정본·충돌이 rev_no 를 따르는 것은 요청된 규칙이지만, 두 현재성의 통일 여부는 설계 결정이다.
- **`stale` 충돌 상태**: 새 마이그레이션 + contract 갱신이 필요해 하지 않았다. 지금은 resolved_* 로 전환한다. 두 당사자가 모두 대체된 경우의 `resolved_both_valid`는 UI 에서 오해될 수 있다.
- **CLI `kb-ingest` 기본 scope 변경**: 기본이 work_only 가 되어, 기존에 scope 없이 수집하던 사용 방식은 personal 검색에 안 나온다. personal 로 두려면 `--scope personal`을 명시해야 한다. 이 호출 지점(운영 스크립트·문서)은 점검하지 못했다.
- `register_text`로 personal scope 재등록할 때 같은 `source_key`의 문서가 접근 행 없는 미상 문서면 404(`KbNotFound`)가 난다. 미상 문서를 personal 로 올리지 않기 위한 fail-closed 결과다.
- 검증 보고서의 프로브와 원출력으로 RED 를 재현하지 못했다(위 "범위와 체크아웃"). 보고서가 지적한 다른 증상이 있다면 이 시험이 덮지 못할 수 있다.
- `matched_entities`는 정본 카드 목록이라 정의 주장이 없는 L1 전용 엔터티는 카드가 없어 비어 있다. 별칭 매칭은 `find_matched_entities`와 `items`로 확인했고 이 동작은 바꾸지 않았다.
- 운영 DB에서 백필 dry-run 결과(미상 문서 수, 분류 분포)는 확인하지 못했다. 운영 DB를 건드리지 않았다.
- 시험·산출물 로그(RED/GREEN 원출력)는 이번 Run outbox 에 있다. 저장소에는 포함하지 않았다.
